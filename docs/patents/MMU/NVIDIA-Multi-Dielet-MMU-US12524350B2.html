01 / PATENT STUDY

核心结论：把同步边界放在 HUBMMU

US12524350B2 提出一种多 dielet MMU 协作方式：让软件看到一个逻辑 GPU / MMU，同时保留每颗 dielet 的本地翻译资源，并按操作类型决定在哪里协调。

设计核心：“在哪里产生请求”“在哪里确定处理顺序”“在哪里执行本地工作”“在哪里收齐结果”可以是不同位置。Bind / invalidate 在 primary 协调，各 dielet 并行执行；普通 page walk 在本地推进；ATS 对外通信由活动接口所在的 dielet 汇聚。[说明书网页段 0049–0057][说明书网页段 0108–0120]
状态变化

跨 dielet 协调

对影响共同地址空间的绑定、失效等操作，分发统一请求，再等待各自本地状态更新完成。

高频路径

本地翻译并行

本地 TLB 查询、页表遍历及 PDB / PDE / PTE 缓存保持独立，普通 miss 无需统一进入 primary 的队列。

对外服务

接口决定出口

C2C 示例中由 secondary 汇聚 ATS，但请求生成和最终回填仍属于各自的发起 MMU。

阅读重点

语义一致，局部状态可不同

各 dielet 不必拥有相同的 TLB 内容或 PDB ID；需要一致的是上下文含义、失效范围以及对外完成条件。

阅读路线：技术背景 → 创新点 → 状态与硬件 → Bind / 失效 / ATS → 完整场景 → 性能与实现难点。

02 / PATENT STUDY

技术背景：多裸片为何把 MMU 问题放大

从单 die 的资源扩展，走向单逻辑设备的状态协调

专利的出发点是：GPU 并行计算需求持续增加，而单 die 上继续集成更多单元会面对散热、互连实现、信号与器件尺寸等限制。将多个独立制造的 dielet 互连，可以扩大处理资源；但如果每颗 dielet 仍按独立 GPU 的方式暴露给软件，驱动就必须认识拓扑并显式协调多个 MMU。该方案希望把这种协调放到硬件中，让软件在较大程度上沿用单体 GPU 的设备视图。[说明书网页段 0003–0006][说明书网页段 0023–0027]

这个目标不只要求“大家能访问同一片内存”。MMU 还决定某个引擎当前属于哪个地址空间、一个虚拟地址指向哪一物理位置、当前访问是否被允许、何时可以认为一次状态变更已经完成。这些判断分散到多个 dielet 后，任何一处残留旧状态都可能影响整个逻辑设备的行为。[说明书网页段 0031–0035]

场景未经协调时会出现什么问题本专利对应机制
上下文绑定 / 切换同一引擎标识在不同 dielet 上可能指向不同页表根，导致后续翻译使用不同上下文。Primary 获取并分发 Bind 信息；本地与跨 dielet 两级确认。
映射 / 权限变化D1 已删除旧翻译，D2 仍可能在 TLB 命中旧物理地址或旧权限。失效请求覆盖全部参与 dielet，分别执行并汇总 ACK。
只有一个活动外部翻译接口某 dielet 产生 ATS，却没有本地可用 C2C；返回结果也必须找到最初的请求。指定 dielet 汇聚请求并按目标 / 来源标识分发响应。
故障和访问记录分散软件需要从多个报告出口拼接故障，或遗漏另一 dielet 观察到的物理内存访问。Fault 统一报告；VAB 本地跟踪、汇总写回。

“多 GPU 互连”与“一个逻辑 GPU”差在哪里

互连首先解决消息和数据能否到达；单逻辑 MMU 还必须定义操作的作用范围与完成语义。专利强调，若缺少其硬件同步机制，软件就需要像协调多个独立 GPU 那样处理各 MMU。这里的工程目标是把依赖物理拓扑的协调尽量收进 HUBMMU，而不是要求所有缓存、所有接口和所有请求都变成完全相同。[说明书网页段 0025–0027][说明书网页段 0047–0053]

教学对照 后文比较“全部集中”或“全部交给软件”的方案，是为了说明设计取舍，不代表专利提供了这些方案的实现或性能测量。

03 / PATENT STUDY

六个技术创新点：按问题、机制和效果拆解

这里将“创新点”具体化为专利提出的结构与协议组合。基础部件如 TLB、页表遍历、ATS 本身只是背景；重点在于它们如何在多个 dielet 间协作。

设计点具体机制技术意义及约束
1. 按操作分类，而非全部集中需要统一状态变化的请求送到指定 MMU；普通地址翻译由发起 dielet 的 MMU 处理。把高频本地处理与较低频控制协调分开。是否得到性能收益取决于请求比例和队列负载。
2. 允许不同类型采用不同协调点Primary 处理 Bind / 失效等；活动 C2C 所在 secondary 汇聚 ATS。协调角色与实际服务位置匹配；primary 不是所有流量的必经点。
3. 排序集中，执行分散，完成汇总先由协调点组织请求；各 dielet 更新本地 TLB；最终完成等待本地和远端 ACK。把全设备操作拆为局部可并行工作，同时保留统一完成边界。
4. 同步语义，而不镜像缓存索引PDB cache 独立，同一页表根的本地 PDB ID 可以不同；各方按输入 PDB 解析本地 ID。允许本地缓存分配和工作集不同，跨 dielet 消息使用可被对方解释的上下文。
5. 分布式 ATS 生成与集中回包路由各 HUBMMU 并行生成 ATR，指定出口仲裁发送，ATRsp 携带可定位原始目标的信息。既共用外部接口，又让翻译结果回到正确 dielet 和本地表项。
6. 将报告、统计与身份纳入逻辑设备Fault 从各 dielet 汇入 primary；VAB mask 汇合；角色 / dielet ID 由配置决定。单逻辑 MMU 不止包含翻译路径，也包含软件可观察的错误与设备状态。

为什么不把所有 page walk 都交给 primary？

工程推断 如果所有 miss 都跨 dielet 集中处理，primary 的请求入口、遍历上下文和下游访存能力可能一起成为共享瓶颈；远端请求还会增加来回转发。该专利让常规翻译保持本地，只对确实需要统一视图的操作建立协调路径。反过来，若所有控制操作也完全本地化，就需要另一个层次负责全局失效和完成判定，问题并不会消失。

教学对照资源组织需要付出的代价
所有翻译集中统一入口、集中 walker / 缓存共享入口竞争；远端 miss 增加转发。不是本文采用的组织。
每个 MMU 完全独立，由软件协调硬件本地自治软件需要知道参与者、分发操作并等待多个完成。
本专利的混合组织本地翻译 + 按类型指定协调点需要跨 dielet 消息、请求身份、两级 ACK 和正确的操作顺序。
04 / PATENT STUDY

硬件层级与关键数据结构

从软件视角到物理实现

专利希望 CPU 驱动在相当程度上把多 dielet GPU 当作一个单体处理器使用。每个 dielet 仍保留硬件引擎、MMU 和本地缓存；承担跨 dielet 协调的是各 dielet 的最高层 MMU，即 HUBMMU。这一层的协作构成软件可见的单个逻辑 MMU。[说明书网页段 0024–0033]

查看专利原图 FIG. 1：两个 dielet 组成一个逻辑 GPU，CPU 驱动通过外部接口访问
术语 / 单元在本文中的准确位置容易混淆的点
Dielet单独制造、与其他 dielet 互连组成更大处理器的裸片。例图用两个，说明书并不限于两个。“Dielet”是物理划分；“逻辑 GPU”是对软件呈现的设备视图。
HUBMMU / Fill unit每个 dielet 的顶层 MMU；fill unit 可包含 bind table、PDB cache、fault 状态机和 ATS wrapper。“一个逻辑 MMU”不意味着只有一个物理页表遍历器。
GPCMMU / HSHUBMMU组件级 MMU，服务本 dielet 的组件。它们跨 dielet 的协调经本地 HUBMMU 进行，示例中不直接与另一 dielet 的同级 MMU 对话。
TLB hierarchyuTLB、GPC L1/L2 TLB、Link TLB、HUBTLB 等翻译缓存层级。L1/L2 TLB 缓存的是地址翻译；不要与 L1/L2 数据缓存混同。
Bind table把引擎 / 上下文与用于地址翻译的绑定信息联系起来；示例按 engine ID 索引。更适合从“引擎 → instance block / 页表根”理解，而不是直接视为最终 VA→PA 的 TLB。
PDB cache / PDB ID缓存用于页表遍历的根信息；PDB ID 是各 dielet 本地使用的标识。同一页表根在两个 dielet 上可以有不同 PDB ID；相同 ID 数值也可能指向不同页表。
PDE / PTE cache缓存页目录项 / 页表项，加速本地 GPU 页表遍历。这类遍历缓存与缓存最终翻译的 TLB、缓存根信息的 PDB cache 需区分。
FBHUB承载页表遍历所需内存读写，以及部分响应、ACK、故障包或 VAB 数据等流量。“本地 FBHUB 发出”不保证目标内存也在本地 dielet。
HSHUB连接高速接口，示例中承载 ATS / ATSD 的请求、响应和 ACK。HSHUB 不是跨 dielet 同步的唯一通路。

同步通道与内存通道有分工

说明书允许 HUBMMU 之间使用私有总线，或经 dielet-to-dielet crossbar 的连接。传送的包可包括 Bind、TLB invalidate、ATR、ATSD、ATRsp 数据、内部 fault、VAB 以及相关 ACK。部分实现允许其他部件共享该连接；另一些通信和数据搬运可以经过 FBHUB。不能把图中的一条逻辑箭头理解成所有实现都必须独占同一根物理总线。[说明书网页段 0048][说明书网页段 0056]

HUBMMU 还可配备收发队列，以及 blocking / non-blocking 两类发送线程。原文举例将 Bind、失效、blocking fault、VAB、ATS 等放在 blocking 类，将 non-blocking fault 及其 ACK 放在另一类；没有给出完整的优先级、信用流控或死锁证明。[说明书网页段 0057]

需要一致的状态，与允许不同的状态

状态层次各 dielet 的关系跨 dielet 操作依赖什么
引擎 / 上下文 → 页表根的绑定含义相关全局引擎索引应得到一致的绑定信息。Bind 传递 engine ID、PDB 信息和映射后的 instance-block pointer。
本地 PDB cache 槽位独立分配；D1 的 ID=3 与 D2 的 ID=3 不保证代表同一根。接收方根据 PDB 自行查询本地 ID；不直接照搬远端索引。
本地 TLB 和 PDE / PTE cache 工作集命中、替换和已缓存条目可以不同。相关失效需覆盖所有参与者已有的目标翻译；不要求先镜像缓存内容。
请求来源和返回目标本地名字需要在跨 dielet 传输后仍可识别。originating hub / requester ID、dielet ID、target ID 等字段按消息类别使用。
全设备完成状态仅完成本地部分不足以对外宣告全局完成。协调点汇总本地及各远端的完成信息。

地址翻译一致性与数据缓存一致性是两类问题

TLB 保存“去哪里访问、是否允许”的结果；数据缓存保存“那里有什么数据”。本专利的主要同步对象是前者以及与之相关的控制状态。一次 TLB invalidate 不等价于回写所有 L2 脏数据，也不能单凭 ATS 支持推出 CPU/GPU 间的完整数据一致性协议。正文仅将硬件内存一致性列为某些 C2C 实现可具备的能力。[说明书网页段 0083][说明书网页段 0104]

06 / PATENT STUDY

Bind：先建立一致的翻译上下文

Bind 的核心语义：把一个硬件引擎与 instance block 关联起来，instance block 含对应页表指针。后续来自该引擎的内存请求，才能找到正确的地址空间。专利把 Bind 视为分配工作之前的重要前提之一。[说明书网页段 0063][说明书网页段 0076]

以请求来自 secondary 为例

  1. 入口转发（402b / 402c）：dielet 2 的引擎向 HUBMMU-2 发出 Bind；HUBMMU-2 根据 secondary 角色转发至 HUBMMU-1。
  2. 形成统一处理顺序（404 / 406）：HUBMMU-1 接收本地和远端 Bind，可先排队、再仲裁选择要处理的请求。
  3. 获取 / 建立绑定信息（408 / 410）：primary 处理选中的 Bind 并发送相关信息；示例字段包括 engine ID、PDB cache 信息、映射后的 instance-block pointer。
  4. 各 dielet 更新本地状态（412 / 414a / 414b）：secondary 更新自己的 bind table，双方把必要绑定信息传播到本地相关 TLB。
  5. 局部确认，再全局完成（416a / 416b / 418 / 420b / 420c）：primary 等本地 TLB 与 secondary 的确认，再让请求源收到 Bind 完成。

为什么只让 primary 获取 Bind 所需内存信息？

原文明确指出，对一个 Bind 请求，由 primary 访问内存来服务该 Bind，不论请求源在哪个 dielet。由此取得的信息再分发到其他 dielet，随后各 dielet 独立更新本地状态。工程推断 这有利于让同一次 Bind 使用同一份上下文来源，并避免各 dielet 对相同 Bind 重复取数；专利没有给出量化收益。[说明书网页段 0077–0078]

“绑定含义一致”不等于“缓存槽号一致”。两个 dielet 的 bind table 和 PDB cache 是独立的，本地替换与 ID 分配可以不同。需要保持的是同一引擎 / 上下文对应的页表语义。原文一方面说同 engine ID 的绑定信息相同，另一方面明确允许本地 PDB ID 不同，应按此区分语义信息与本地编码。[说明书网页段 0053][说明书网页段 0065]

绑定操作究竟更新什么：以引擎 E 切换地址空间为例

教学示例 假设引擎 E 之前关联页表根 Rold，现在要关联 Rnew。Bind 同步的核心是让各相关位置今后都按 Rnew 解释 E 的请求。D1 可以把 Rnew 放在本地 PDB 槽 3，D2 可以放在槽 11；两边的“槽号”不同，并不造成地址空间含义不同。[说明书网页段 0053][说明书网页段 0063–0065]

实现中至少要区分三件事：引擎绑定到哪个 instance block、该 block 提供哪个页表指针、这个指针在本地缓存中用哪个 ID 表示。因此，跨 dielet Bind 信息带的是用于重建绑定含义的资料，接收方再更新本地数据结构。原文也允许 bind table / PDB cache 按全部 dielet 的引擎规模配置，这与“普通请求仍由本地 MMU 服务”并不矛盾。[说明书网页段 0065][说明书网页段 0072–0074]

为什么需要两个层次的握手

  • Dielet 内：HUBMMU 更新相关组件级 TLB 后，收集本地 ACK，确认消息已在本地层级得到处理。
  • Dielet 间：Primary 等待自身本地完成和其他 HUBMMU 的完成，再向原始请求引擎返回一次完成。
  • 工作分配边界：正文指出，引擎在 Bind 完成后可由 work distributor 分配工作。因此 ACK 是上下文就绪的可观察边界，而不只是“消息已经收到”。

[说明书网页段 0074–0078]

实现细节的边界：这是绑定传播与完成流程，原文没有把上下文切换期间所有旧访存如何排空、全部类型操作如何相互排序逐一写全。这里不把 Bind ACK 扩大为“所有旧数据访问已在全系统提交”。

页表遍历：由各 dielet 保留本地处理能力

单个逻辑 MMU 并不要求所有地址翻译都经过 primary。正文强调，各 dielet 的引擎由本 dielet 的 MMU 服务，HUBMMU 独立执行本地页表遍历，不需要从另一个 HUBMMU 取得页表遍历状态。[说明书网页段 0050][说明书网页段 0092–0102]

查看专利原图 FIG. 3：每个 dielet 的 TLB 层级，以及 HUBMMU 中的 fill unit

FIG. 6A 的路径

  1. 引擎发起内存请求（602）；本地 TLB 查找 miss（604）。
  2. 本地 fill unit 根据引擎在 bind table / PDB cache 中的绑定信息开始 GMMU page-table walk。
  3. 当需要的页表信息不能在缓存中取得时（606），HUBMMU 向本地 FBHUB 发起页表内存读取（608）。
  4. FBHUB 经内存 crossbar 到达目标内存并取得信息（610 / 612）；内存可以是 GPU 显存，也可以经 C2C / PCIe 访问系统内存。
  5. 响应沿反向路径回到本地 HUBMMU（614），更新本地翻译相关表 / TLB（616），再响应请求引擎（618）。

每个 HUBMMU 可有自己的 PDE / PTE cache，用于加速遍历。遍历中如果需要 ATS，则调用后面介绍的 ATS 路径；这不改变“遍历由本地发起和推进”的基本分工。[说明书网页段 0093–0102]

“本地页表遍历”限定的是控制主体。它不保证页表数据物理上只在本 dielet，不保证完全没有跨 dielet 流量，也不保证不访问系统 MMU。它说明普通 page walk 无需先把整个请求交给 primary 排队。

为什么这一部分适合分布式执行？

工程推断 地址翻译属于高频路径，让各 dielet 使用自己的翻译缓存与遍历资源，可以避免所有 miss 都争用一个中央遍历器。需要跨 dielet 统一的状态变化通过 Bind / invalidate 等控制操作维护；高频查找保留局部性。这是一种控制操作集中、常规处理分散的取舍，不是专利提供的实测性能结论。

页表根、页表项和最终翻译不能混成一个缓存

Bind / PDB 提供“从哪一棵页表开始”；PDE / PTE cache 缓存遍历中间结果或页表项；TLB 缓存已经取得的翻译。对同一 VA，换一个上下文可能得到完全不同的 PA，因此引擎身份与绑定信息是遍历的前提。页表读取又是实际内存事务，需要消耗 FBHUB、crossbar 和目标内存带宽。[说明书网页段 0039–0041][说明书网页段 0063][说明书网页段 0093–0100]

工程推断 若页表多级且多次 miss，下一层地址通常依赖上一层结果，单次 walk 可能存在串行依赖；多个 walk 则有机会并发。这解释了为什么本地 walker 和页表项缓存有价值，也解释了为什么“加一颗 dielet”不能保证翻译吞吐线性增加：目标内存或 ATS 出口仍可能共享。

正文较早的 PDB cache 描述存在把根缓存与直接翻译命中混写的措辞。这里依据 Bind 和 FIG. 6A 的具体流程分层讲解，不据此推导未披露的统一缓存微架构。

ATSD 只针对标识为 ATS 的翻译缓存条目。其内部消息流复用 TLB invalidation 的组织方式：HUBMMU-2 把外部 ATSD 当作需要转交 primary 的失效请求，primary 启动各 dielet 的更新并收集确认。[说明书网页段 0120]

ATS 请求上下文为何必须在跨 dielet 往返后仍可恢复

当 D1、D2 都能产生 ATR，而对外只使用 D2 的接口，返回入口本身无法告诉硬件“这个结果属于谁”。原文因此列举 target ID，以及可选的 dielet ID、ATS cache ID、cache line ID、entry ID，用于识别目标并更新源端本地表。它们分别服务于回哪颗 dielet、回哪个目标 / 缓存、对应哪个待处理位置；原文未固定所有字段的组合编码。[说明书网页段 0108–0111]

工程示例 若 D1 和 D2 都有一个本地 entry 7，仅凭“7”不能判断应回填哪一颗 dielet。可以通过包含来源的标识或出口处的映射记录解除歧义；专利列出相关标识，但没有规定必须采用本例的具体表结构。

“串行化发送”不等于“一次只能有一个未完成 ATR”

正文一方面描述排队 / 仲裁，另一方面给出每来源可接纳 256 个、合计 512 个 ATR 的配置示例。合理的阅读是：共享出口要决定哪些请求先发送，但可以保留多个未完成请求。不能把 serialize 直接解释为“一定等上一笔响应回来才发下一笔”，也不能把容量上限当成每周期吞吐。[说明书网页段 0108][说明书网页段 0114]

ATS 可以处在翻译链的不同位置

原文描述两类例子：从虚拟地址取得物理地址，或先进行 GPU VA → GPU PA，再把 GPU PA 翻译到 system PA；生成 ATS 的类型可以取决于 page walk 进行到的层次。这说明 ATR 不只是“用户数据页最终翻译”的单一固定步骤。具体地址格式、各级页表模式与平台协议仍未给出完整定义。[说明书网页段 0105–0106]

实现关注点 多来源汇聚还需处理出口排队、公平性、响应资源占用和回压。按来源给出容量示例并不能证明某种特定仲裁公平性；两个来源若同时形成 miss burst，吞吐仍受 HSHUB、C2C 和 SMMU 服务能力约束。

Fault 与 VAB：统一报告和全设备访问记录

Fault：检测分散，报告集中

TLB 或 HUBMMU fill unit 可以在各 dielet 独立检测访问异常。secondary 将内部故障信息转给 primary，由 primary 生成统一对外报告；信息可包含故障类型 / ID、参数、发生故障的引擎或客户端及源 dielet ID。报告可以写入故障缓冲区、寄存器或采用其他手段。[说明书网页段 0122–0128]

FIG. 6C 的顺序是：D2 引擎发请求（632）→ HUBMMU-2 检测故障（634）→ 向 HUBMMU-1 报告（636）→ HUBMMU-1 对故障报告排序，并通知 CPU / SMMU 等处理实体（638）。专利这一流程到“报告”为止，没有详细定义 OS 缺页处理、页面迁移、重放或恢复策略。

查看专利原图 FIG. 6C：dielet 2 检测到故障，由 dielet 1 对外报告
工程推断 统一报告有利于让驱动只面对一个逻辑故障出口。但必须保留足够的源身份才能定位具体引擎；不能因为对外合并成一个设备，就丢掉 dielet-local 的来源信息。

VAB：合并各 dielet 观察到的显存访问

VAB（vidmem access bit）用于追踪自开始跟踪或上次 dump-and-clear 后，哪些物理内存片段被访问或修改。原文给出每个 dielet 独立维护掩码（例如 4K bits）的示例，可服务分页、调试、虚拟机交换等用途。[说明书网页段 0129–0130]

  1. 主机可把 VAB dump 请求编码为 TLB invalidation 包中的一个字段，但这类请求并不执行 TLB invalidation。
  2. HUBMMU 将 dump 请求通知其他 dielet；每个 dielet 从自己的跟踪副本中独立收集 VAB。
  3. secondary 把本地合并后的 VAB mask 分成多块发给 primary。
  4. primary 合并本地与远端掩码，并写入内存。

[说明书网页段 0131–0135]

原文段 0052 强调 primary 发起 VAB dump；段 0130–0132 又描述收到请求的 HUBMMU 与另一方之间的转发。在总结中将“接收 / 转发”与“最终汇总写回”区分，避免把这几句压成所有情况下都只有同一方向的入口路径。4K bits 是掩码长度示例，不能据此推导内存页大小为 4KB。

Fault 统一出口仍需保留定位信息

教学示例 若 D2 的一个 CE 因权限检查失败产生 fault，内部报告至少需要让接收者区分“哪一类错误、哪个请求相关参数、哪个引擎 / 客户端、哪颗源 dielet”。Primary 的任务是把这些局部事件组织成软件可读取的故障包，而不是将所有事件丢失来源地合成一个匿名错误。原文列举这些字段，但未规定完整故障记录布局。[说明书网页段 0122–0128]

VAB 合并不仅是数据汇总，也涉及采样时点

若把每一位理解为“某物理区域自上次清除后被访问过”，多 dielet 的集合并可用 OR 来解释，这正是前面图解的教学模型。但专利只规定各方收集、远端分块发送和最终 merge，没有给出每位粒度及合并电路。[说明书网页段 0129–0135]

工程推断 要把最终 mask 用作精确的统计窗口，还需定义收集 / 清除期间新访问归属哪个窗口，以及各 dielet 的采样边界如何对应。正文没有展开全局冻结、双缓冲或原子快照协议，因此不能仅凭“合并掩码”认为所有位都来自严格同一时钟瞬间。4K bits 是示例 mask 长度，既不是 4KB 页大小，也不能直接推出覆盖的总显存容量。

相同硬件可以承担不同角色

Dielet 可使用相同或近似相同硬件，再通过 fuse / register 设置 dielet ID、primary / secondary / standalone 角色，以及活动接口。制造时相同并不意味着运行时每个端口都启用；角色也不意味着 secondary 的本地 walker 闲置。寄存器可分别由软件编程，原文没有承诺任意寄存器写入自动广播到所有副本。[说明书网页段 0024][说明书网页段 0046][说明书网页段 0054–0055][技术依据：授权文本 17][技术依据：授权文本 18]

标识分两层：全局可识别的引擎，以及本地缓存索引

多 dielet 可能各有“本地 engine 3”，但跨 dielet 的 Bind、故障或返回路由不能只依赖会冲突的本地名字。专利涉及根据 dielet-identifying fuse 取得唯一 dielet 身份，并让各 dielet 的重映射电路按该信号决定 engine ID offset。与此同时，PDB ID 仍可由本地缓存独立分配。全局引擎身份需要可区分，本地缓存 ID 不需要全局统一。[说明书网页段 0033][说明书网页段 0053][技术依据：授权文本 21][技术依据：授权文本 22][技术依据：授权文本 23]

教学模型：global_engine = local_engine + offset(dielet)

例如 local engine 3 配合两个互不重叠的编号区间，可以得到两个不同的全局编号。这里没有填具体 offset，因为文本未规定偏移量、编号宽度、每 dielet 最大引擎数或异构引擎的完整编码。设计上还需确保各区间不重叠，并使请求和响应两侧采用相容的解释。

把机制串起来：三个端到端技术场景

以下场景用于把分散的机制放回一次实际操作中。表内区分原文已给出的消息行为，以及系统集成时仍需补齐的条件。

场景一：D2 上的引擎首次在某地址空间执行

步骤状态变化 / 消息路径关键含义
1. 建立绑定D2 引擎 → HUBMMU-2 → HUBMMU-1；primary 取 Bind 信息并分发。选择正确的 instance block / 页表根。
2. 确认上下文就绪D1、D2 更新相关本地状态，逐级返回 ACK。原文允许 Bind 完成后分配工作；尚未发生具体数据页的翻译。
3. 发出内存请求引擎发 VA；先查本地 TLB；miss 后由 D2 的 fill unit 取本地 Bind / PDB。本地 MMU 推进常规翻译，无需把整个 miss 交 D1。
4. 读取页表 / 按需 ATSD2 经 FBHUB 取页表；如果需要 ATS，经活动接口发出。控制在本地，不保证页表数据也物理本地。
5. 回填和后续命中翻译结果更新 D2 本地表 / TLB，响应引擎。D1 不需要同步填入完全相同的一条翻译。

场景二：已有映射 VA → A 需要改成 VA → B

  1. 系统先准备新映射：页表项更新及其对 walker 的可见性由相应软件 / 内存系统规则保障，这是场景前提。
  2. 发起匹配上下文的失效：请求若来自 D2，先转给 primary；携带 VA、PDB 等用于匹配及返回的信息。
  3. 各 dielet 独立执行：D1 / D2 分别把 PDB 解析为本地 ID，在各自 TLB 层级处理目标翻译。
  4. 汇总完成：primary 收齐各方 ACK；带 system membar 的请求还涉及条件性 I/O flush。
  5. 后续访问重新取得翻译：不应继续使用已被本次失效覆盖的旧缓存结果；在途旧访问、迟到回填和物理页回收仍需完整实现协议配合。

步骤 2–4 的分发 / 确认来自原文；步骤 1、5 是解释映射更新所需的系统上下文，不是本文补造的 NVIDIA 驱动调用顺序。[说明书网页段 0080–0091]

场景三：SMMU 要撤销 GPU 已缓存的 ATS 翻译

外部 ATSD 从 C2C 进入 D2，HUBMMU-2 将它送往 D1；D1 组织全 dielet 的 ATS 条目失效，所有参与者完成后，ACK 再经 D2 的 HSHUB 返回 SMMU。这里外部接口位置与全局失效协调位置并不重合，因此回包闭环包含两次角色交接。若在 D2 刚收到 ATSD 时就直接回复，便跳过了 D1 和其他参与者的实际完成条件。[说明书网页段 0120]

工程取舍：收益、瓶颈与扩展问题

本节为工程分析 下列判断从已披露结构出发，用于理解设计代价。专利没有提供吞吐、延迟、面积、功耗或不同实现之间的测量结果。

维度该方案可能得到的收益仍需处理的代价 / 限制
软件接口把多个物理 MMU 的协调放到硬件内，减少驱动对 dielet 拓扑的直接处理。“软件透明”是设计目标，仍可能需要角色初始化、全局 ID、寄存器配置和错误处理。
常规地址翻译各 dielet 独立利用本地 TLB、PDE/PTE cache 和 page walker。相同页表信息可能在多个 dielet 重复缓存 / 读取；缓存独立不等于没有重复工作。
Bind / 失效一致性指定入口形成处理顺序，再分发到所有 dielet。集中点的队列和仲裁可能成为高频控制操作的瓶颈；完成还要等最慢参与者。
ATS 外部接口集中利用实际存在 / 启用的 C2C 端口，统一管理返回路径。远端 ATR/ATRsp 增加 dielet 间转发；汇聚点需要容纳多个来源的未完成请求。
异常可见性对驱动呈现统一故障报告出口。必须保留来源标识；队列阻塞、故障风暴和报告缓冲容量需要设计。
独立 PDB cache允许各 dielet 自主分配本地 ID、保留不同的工作集。跨 dielet 消息必须传递对方能解释的上下文，而不能盲用源端本地索引。
N-dielet 扩展普通翻译资源随 dielet 数量分散。广播失效、ACK 汇聚、VAB 收集随参与者增加；互连拓扑和仲裁可能需要变化。

参与者增加时的控制流量

若采用简单星形“primary 向 N−1 个其他 dielet 各发一次、各收一次 ACK”的模型，远端控制消息数量约为 2(N−1)，再加请求进入 / 返回消息。这是本报告假设的计数模型，原文未规定广播实现、打包合并、组播支持或物理 hop 数。

Bind / 全设备失效协调点排队、分发、最慢 dielet 的本地完成、ACK 返回及可选 flush。不能据并行失效声称常数时间、零同步开销或全部请求共用总顺序。

更细的失效延迟与 ATS 容量模型

T_invalidate ≈ T_queue + maxᵢ(T_dispatch,i + T_local,i + T_ack,i) + T_reply [+ T_flush]

教学模型 上式把各 dielet 的传播、局部工作和回包都计入，默认这些分支可以重叠。它比简单求和更能表现“最慢参与者决定完成”的现象；原文没有给出任何项的数值，flush 也仅在需要时出现。

平均未完成 ATR 数 N ≈ 完成速率 λ × 平均往返时间 L

这是稳定负载下的排队关系，用于说明为何较长往返需要更多未完成请求资源来支撑吞吐；若可用容量为 C，则容量方面要求 λ × L 不超过 C。它不是性能预测：接口带宽、SMMU 处理和仲裁可能更早成为瓶颈，专利的 256×2 示例也不能直接代入为所有实现的固定 C。
