01 / READING MAP

先把四条边界分清

OS 边界、通信域边界、地址空间边界和完成边界彼此独立。大多数疑问都来自把其中两条当成同一条。

多个 OS，仍可 scale-up

NVL72 的 Multi-Node NVLink 把多个计算节点纳入同一个 NVLink fabric；scale-up 不要求全系统只有一个 OS。普通服务器通过 IB / RoCE 互连则通常属于 scale-out。

可远端访问，不等于同一 VA

导入方拿到自己的 GPU VA。该 VA 经 fabric 寻址到达目标显存；不要求导入方和导出方的指针值相同，也不要求共享进程页表。

异步搬运，不等于零 SM

TMA 让硬件搬数据，但发起、计算、等待与信号发布仍可能运行于 SM。CE 可以承担不含归约计算的复制，是否零 CTA 取决于实际路径。

本地完成，不等于全体退出

本 rank 的 AllReduce 完成，保证本地输出可按 stream 次序消费；本地 event 不证明其他 rank 的 kernel 已经退出。

阅读顺序建议：先看 通信域和地址路径，再跟随 TP 示例理解 NCCL，最后比较 MoE、EP 专用库与搬运引擎。新增阅读路线：Scale-out 方案 → 通信优化 → Attention head TP → MLA 的张量与缓存。如果只关心代码里的完成标志，直接看CUDA event和完成语义。

API 保证来自 CUDA / NCCL 的接口契约。公开源码解释某个可检查的实现路径。教学模型用于推理，不宣称是芯片完整框图或每个版本唯一实现。

本文统一修正几个容易被简化过度的说法：不把 NCCL 等同于 NVLink；不把 C2C 等同于交换式 GPU fabric；不把 TMA 等同于 CE；不把本地 event 等同于全局 barrier。

02 / TOPOLOGY & DOMAINS

跨 OS 并不决定 scale-up 或 scale-out

“两张 GPU 能否跨 OS 通信”的答案是可以，但需要区分底层链路。NCCL 支持多进程、多节点；它既能使用 NVLink，也能使用网络 transport。NVL72 的特殊之处是多个节点可共享一个多节点 NVLink 域，而不是 NCCL 把普通网络变成了 NVLink。[01][02][09]

场景典型节点间路径如何描述
单服务器，多 GPUNVLink / NVSwitch，或 PCIe通常讨论本机 scale-up；具体带宽与直连能力取决于拓扑。
两台普通 GPU 服务器，各自 OSGPU → NIC → IB / RoCE / Ethernet → NIC → GPU节点间通常是 scale-out；服务器内部仍可存在 scale-up 域。
NVL72 的多个计算节点，各自 OSGPU → NVLink Switch Fabric → GPU同一 MNNVL 域内属于 NVLink scale-up。
多个 NVL72 域互连域内 NVLink，域间通常经网络同时具有 scale-up 与 scale-out 两层。

跨 OS NVLink 需要的系统条件

支持 MNNVL 的硬件拓扑、配套驱动与系统软件、健康的 fabric，以及可跨 OS 导入的内存对象和访问权限需要共同成立。普通 NVLink 桥接或任意两台插有 GPU 的服务器，并不自动具备这种能力。这里讨论的是受支持的平台部署，不是在承诺任意 Linux / Windows 混合 OS 都能互操作。[01][02][03]

NVLink-C2C 与 GPU fabric 要分开画。Grace–GPU 的 C2C 服务于 CPU–GPU 互连与一致性体系；GPU 经 NVSwitch 访问其他 GPU 的路径，不应仅凭名称被归到“C2C MMU”。一个系统可以同时具有两种链路。[08]

后文统一使用 4 个 rank、4 张 GPU、2 个 OS 的教学子集：OS A 上为 G0/G1，OS B 上为 G2/G3。真实 communicator 可以覆盖 NVL72 的一部分或更多 GPU；一个 OS 可以运行多个进程，一个进程也可以管理多个 GPU。OS、进程、rank 与 GPU 不是天然一一对应。

03 / CONTROL PLANE

谁搭好环境，谁协调同一次 collective？

组件主要职责不应误解为
FM / NVLSM配合驱动管理 fabric，涉及拓扑发现、交换路由、分区与系统配置；具体分工随平台变化。每次 AllReduce 的中央调度器，或 tensor 的 CPU 中转站。
IMEX + GPU 驱动跨 OS 内存导出、导入的控制与权限；建立、维护所需的 fabric 映射生命周期。每个 NVLink load/store 都必须经过的用户态数据代理。
框架 / MPI / 分布式 store组织 rank、并行组和初始化信息；分发共同的 NCCL Unique ID。每轮都向 72 张卡广播“现在做第 5 个 chunk”的 CPU 控制循环。
NCCL host 端建立 communicator、连接、拓扑与算法资源，把 collective 工作提交到本地 stream。一个驻留在某台 OS 中、代表所有 GPU 执行计算的服务。
NCCL device 协议 / 对应引擎根据算法的数据依赖、进度计数与流控推进本次操作；网络路径还可能涉及 proxy / NIC。只要本地 API 被调用，就能忽略其他 rank 是否参与。

上述控制与导入机制见 IMEX / MNNVL 文档；NCCL communicator 的成员与初始化由其 API 定义。[01][02][09]

两边的 NCCL 如何加入同一个组？

// 伪代码：假定每个进程管理一张 GPU，world_size == 4。
if (global_rank == 0) ncclGetUniqueId(&id);
bootstrap_broadcast(id);  // MPI / socket / framework store 等带外通道

cudaSetDevice(local_device_index);
ncclCommInitRank(&comm_i, 4, id, global_rank);

// 每个 rank 在同一 communicator 中，以匹配的调用顺序参与。
ncclAllReduce(S_i, Y_i, count, dtype, ncclSum, comm_i, stream_i);

共同的 ID、成员数和不同的 rank 编号建立同一个逻辑通信组。comm_i 是各进程自己的句柄，数值不必相等；local_device_index 也不等于全局 rank。NCCL 会交换连接与拓扑信息，具体 bootstrap 连接的组织由实现决定。[09]

“同一次 AllReduce”依靠同一 communicator 中匹配的 collective 顺序和参数，包括操作类型、count、数据类型与 reduction op。概念上可视为各 rank 都执行了该组的第 k 次操作；不能把任意不匹配调用交给 NCCL 自动配对。顺序或参数不匹配可能挂起、报错或产生错误行为。[10]

A 先调用，B 还没调用，会发生什么？

A 可以先完成主机提交。它的设备通信工作若已启动，能够先处理当前可推进的部分；到需要 B 的数据、ready 或 credit 时，便停在协议条件上。B 随后启动对应工作，发布所需进度，A 才能继续。具体等待方式取决于算法、协议与执行引擎，不能一概说成“每个 rank 启动后立即做一次全局 barrier”。

当选中 NVLink 路径时，通信缓冲区与 GPU 协议进度通常通过 NVLink 可访问内存交互。TCP 可以参与初始化与控制连接，但它不必承载稳态的数据就绪信号。如果实际 transport 是网络，则可能由 NIC、网络协议、GPU/CPU proxy 等共同完成进度。[01][14]

Fabric Manager 不会替缺席的 rank 调用 NCCL。普通 collective 中，每个成员 rank 都必须提交匹配操作。更低层的一侧通信 API、设备 API 或其他库的远端写入，是另一种编程模型，不能据此省略普通 AllReduce 的参与者。

04 / ADDRESS TRANSLATION

远端访问不是拿对方的指针直接使用

设 G2 分配了一块显存，本地 CUDA 指针为 Y₂。导出相关内存对象并由 OS A 导入后，G0 进程得到自己的映射地址 R₀₂。访问 R₀₂ 最终可触达 G2 的相同物理页，但 R₀₂ 与 Y₂ 可以完全不同。[01][03]

符号属于谁 / 表示什么关键属性
X₀ / Y₂各进程本地 GPU VA用于源数据或目标本地缓冲区；由本进程地址空间解释。
R₀₂G0 进程中，导入 G2 内存所得的 GPU VA仍然是源端发起指令所使用的 VA，不是目标进程指针。
F₂ / FA / FLAfabric 可解释的远端寻址范围本文 FA 是泛称；FLA 特指相关 fabric 线性地址模式，不能与所有 GPA window 模式混同。
P₂[i]目标 GPU 上第 i 个映射页的物理位置连续 VA / FA 不保证底层物理页连续。

准备映射，与每次访问的执行路径不同

VMM 可以把物理内存对象、虚拟地址保留、映射与访问权限拆开管理。跨 OS 导出 / 导入还需要 fabric 句柄与系统授权。驱动在准备阶段建立这些关系；运行时由硬件地址翻译与存储系统处理请求，而不是每个数据包都去找 IMEX 服务做软件翻译。[01][03]

源端指令使用 R₀₂ + δ → fabric 可路由的 F₂ + δ → 目标页 P₂[i] + page_offset

这是一条远端寻址的逻辑链，不是“先访问 G0 本地 PA，再把那个 PA 转成 G2 FA”。导入映射中的属性已经告诉硬件这是 peer / fabric 可访问资源。GMMU 的能力也不应被缩减成“只会 VA → 本地 HBM PA”。[04][05]

FA → PA 是否需要远端 MMU？

在 FLA 地址空间需要映射到目标显存页的模式下，目标端确实需要相应的硬件地址解释 / 翻译机制。公开驱动中，fabric VA space 的建立使用 instance block、GMMU 初始化与 FLA bind 相关接口，说明这不是单纯依赖目标应用的普通 VA 页表。FLA 的映射上下文与目标应用的 Y₂ 上下文可以不同。[04]

但“每个 NVLink 事务必定在远端完整走一次页表”不成立：TLB 可以命中；物理 / GPA window 与 FLA 模式可能有不同路径；虚拟化还可能增加 GPA → SPA 层。应根据平台与实际映射模式判断，不能把某一种架构图变成所有 GPU 的固定公式。[06][07]

如果假设有 GMMU 和 CMMU 两个 MMU，该怎么画？

可以作为教学假设定义两个逻辑职责：源端模块完成应用 VA → fabric 地址，目标端模块完成 fabric 地址 → 目标物理页。仅声明“CMMU 负责 VA → FA”还不足以解释 FA → PA；必须明确目标入口使用哪一个地址上下文、如何找到映射、如何处理权限和 TLB。

公开资料不足以支持“Blackwell 恰好只有两个 MMU，且 CMMU 的含义就是 C2C MMU，并包办这两次翻译”这样的断言。本文保留源端 GPU 地址翻译、fabric 路由、目标 fabric 地址处理、目标存储系统四个逻辑层，不把未经证实的模块名字填进芯片框图。NVSwitch 路由不等于查询进程页表，CPU MMU 也不逐条替 GPU HBM peer 请求做翻译。

对话中的 R₁₂ + δ → F₂ + δ → P₂_phys + δ 在同一映射页内或物理连续区间很直观。跨页时更准确的写法是：page_index = floor(δ / page_size)，再到 P₂[page_index] + (δ mod page_size)。不要从虚拟连续推导出物理连续。

05 / TENSOR PARALLEL ALLREDUCE

一个 128 KiB 的 TP4 输出，如何经过所有 GPU？

以 LLM 中的行并行线性层为例。将收缩维 K 分成 4 份，每张 GPU 计算局部和：Sᵢ = Xᵢ Wᵢ，其中 Xᵢ:[8,K/4]，Wᵢ:[K/4,8192]，所以每张卡的 Sᵢ:[8,8192] 形状相同。AllReduce 做逐元素相加，得到完整 Y = Σᵢ Sᵢ，每个 rank 持有一份。[10][11]

65,536每卡归约元素数
128 KiBBF16 的本地输入 / 输出大小
32 KiB等分成 4 个 chunk 的单块大小

选择 Ring 作为可手算的算法

设环为 G0 → G1 → G2 → G3 → G0。将矩阵展平后分成 C0、C1、C2、C3 四块。逻辑上先做 3 轮 ReduceScatter，让每个 rank 拿到一个完整归约块；再做 3 轮 AllGather，把完整块传给其余 rank。实际 NCCL 可按 channel、slice 流水推进，并把阶段边界融合在 primitive 中；这里的“轮”是教学视图，不是全体卡同时对齐的时钟。[13]

交互：跟踪每个 chunk 已包含哪些 rank 的贡献

单元格内的 0 / 1 / 2 / 3 是贡献来源。绿色表示已经包含四个 rank 的和。静态页面或打印时，下面的文字和计算仍可独立阅读。

初始：各 rank 只有自己的局部贡献

为了展示传播过程，模型保留旧的中间值。实际 NCCL 使用循环缓冲区、direct buffer 等机制，不要求保留这张完整状态表。

以 C2 为例：G3 的 C2 发给 G0，加上 G0 的贡献后发给 G1，再加上 G1 的贡献发给 G2；G2 加上自己的贡献，得到完整 C2。随后这个完整块经过 G3、G0、G1。不同 chunk 同时在环上推进，因此每张卡都在发送、接收与处理其他块。

一次操作的逻辑数据量

每 rank 发送 = 2 × (p − 1) / p × B = 2 × 3/4 × 128 KiB = 192 KiB
每 rank 接收 = 192 KiB；全环累计发送 = 4 × 192 KiB = 768 KiB

本例有两条跨 OS 边：G1 → G2 与 G3 → G0，每条发送 192 KiB，所以跨 OS 累计发送 384 KiB。这仍然是 NVLink 流量，不因为跨 OS 就变成网络 TCP 流量。这里按逻辑链路发送计数，不把同一传输的发送和接收重复相加，也未计协议头、交换机内部跳数、额外 staging 或 padding。

一个粗略模型是 T ≈ 2(p−1)α + [2(p−1)/p]B/β，其中 α 表示逻辑步骤延迟，β 表示有效传输带宽；它忽略归约计算、竞争、拓扑和流水细节，不能拿它直接预测 NVL72 的实测延迟。

NVL72 上为什么不一定真的走这个 Ring？

NCCL 会依据消息大小、拓扑、硬件能力和版本等选择实现，也可能使用 Tree、NVLS / NVLS_TREE 等路径。NVLS 利用支持的 NVLink SHARP / multicast / reduction 能力，可改变归约发生的位置与数据复制方式；普通远端 store 本身不会自动变成求和。应以运行日志、实际 kernel 与注册条件为准。[13][26]

因此，TP=72 不是“有 72 张卡就必须采用”的配置。小 batch 推理时，模型切分、GEMM 效率、通信延迟和并行策略需要一起考虑。本文用 TP4 验证算法因果链，并未声称 Ring 是该 128 KiB 消息在 NVL72 上的最佳选择。

06 / DEVICE PROTOCOL

正确结果来自分块依赖，不来自全局 done 数组

在典型 SM 驱动的 Ring 路径中，host 端提交工作后，GPU 上的 NCCL kernel 执行通信 primitive。公开 all_reduce.h 可看到以下调用家族；它们把接收、归约、输出和转发组合起来，而不是每一步都回到 CPU。[13]

primitive 名称概念作用
directSend发送尚未归约的起始数据块。
directRecvReduceDirectSend接收上游局部和，与本地贡献归约，再向下游发送。
directRecvReduceCopyDirectSend完成该块的最后一次归约，写入本地输出并继续转发。
directRecvCopyDirectSend接收完整块，写入本地输出并转发。
directRecv接收本 rank 最后所需的块。

这是理解数据流的入口，不是所有算法、协议、注册模式都一模一样的指令表。direct 路径还可能改变数据究竟在对端 buffer 还是中转槽中被访问。

接收端到底在等什么？

以 Simple 协议为例，waitPeer 对相应连接的 step / credit 条件进行检查。接收方需要生产者已经发布所需数据；发送方需要对端已经消费旧数据，以免环形槽被覆盖。postPeer 则在满足相应内存次序后更新连接进度。源码中的 system-scope fence 与计数存储一起构成协议，不能替换成“随便写一个 volatile flag”就认为等价。[14]

// 仅表达因果关系，不能作为可直接使用的 CUDA 内存模型代码。
sender:
    wait_until_slot_has_credit();
    write_payload();
    order_payload_before_ready();
    publish_ready_step();

receiver:
    wait_until_required_step_is_ready();
    establish_visibility_for_payload();
    read_reduce_or_forward();
    publish_consumed_credit();

内存顺序的核心是：接收方观察到“可读”时，不能读到尚未完成的旧 payload。实际实现可能把同步与数据布局绑定，LL / LL128 等协议也有不同的标志编码；本文的 head/tail 模型专门解释 Simple 家族，而不是把它套到每种实现上。

等待会占 SM 吗？

若等待逻辑在已经驻留的 NCCL CTA 中执行，答案是会占用某些 SM 资源：寄存器、warp / block 槽位、可能的 shared memory，以及轮询时的访存与指令开销。等待中的 warp 可以让其他就绪 warp 发射，但该 CTA 没有因此自动释放全部资源。占用多少、能否与 GEMM 共驻留，需要看算法与实际 kernel 配置。[14][24]

这与 cudaStreamWaitEvent 在 kernel 启动前建立的依赖不同，也与 CE zero-CTA 路径不同。不能从“CUDA API 异步返回”推导出“GPU 侧没人等待、也不占资源”。

07 / STREAM DEPENDENCIES

逐行解释 GEMM → AllReduce → Residual

先列出对话中的原始结构。每个 rank 都有自己的 S_i、Y_i、communicator、stream 和 event；省略部分假定已完成 device 选择、内存分配和对象创建。

// 每个 rank 都执行；指针与 communicator 都属于本进程。
gemm(..., S_i, compute_stream);                         // 1

cudaEventRecord(gemm_done, compute_stream);            // 2
cudaStreamWaitEvent(comm_stream, gemm_done, 0);         // 3

ncclAllReduce(                                        // 4
    S_i,
    Y_i,
    8 * 8192,      // 元素数，不是字节数
    ncclBfloat16,
    ncclSum,
    comm_i,
    comm_stream
);

cudaEventRecord(allreduce_done, comm_stream);          // 5
cudaStreamWaitEvent(compute_stream, allreduce_done, 0); // 6

residual_add(..., Y_i, compute_stream);                // 7
行CPU 发生什么GPU 上建立什么约束
1 · gemm向 compute_stream 提交计算。产生 S_i；提交成功不等于 S_i 已可读。
2 · record E₁记录 compute_stream 当前已经提交的前序工作。E₁ 完成必须晚于这次 GEMM 完成，而不是 CPU 调用 record 时立刻标记完成。
3 · wait E₁把依赖加入 comm_stream；CPU 不在此等待 GPU。comm_stream 后续 AllReduce 不能越过 GEMM 的完成点。参数 0 是 flags，不是零等待超时。
4 · AllReduce正常 stream 使用下，成功返回表示通信工作已入队。读取 65,536 个 BF16 元素，执行求和，写 Y_i；必须与其他 rank 的调用匹配。
5 · record E₂在 comm_stream 的通信工作之后记录 event。E₂ 完成表示该本地 stream 捕获范围内的通信等前序工作已完成。
6 · wait E₂为 compute_stream 后续工作增加依赖。Residual 只有在本地 Y_i 可用后才能开始。
7 · residual_add提交消费 Y_i 的 kernel。在前述顺序保证下读取结果，不需要为同一条依赖链额外加入 CPU 全局 barrier。

这里使用 CUDA event / stream 与 NCCL 的标准语义；NCCL 非阻塞 communicator、group 聚合提交、CUDA Graph 等高级模式需要遵循其额外规则，不能机械地把“API 返回”当成全部异步状态的完成。[12][15][16][17]

两条 stream 并没有让这三个依赖步骤互相重叠

它们构成 GEMM → AllReduce → Residual 的同一条数据依赖链。若只有这三项工作，放在同一条 stream 上通常也可以表达顺序，从而省去这两次跨 stream event。拆分 stream 的价值在于允许其他独立工作在没有数据冲突、资源足够时与通信重叠。

stream 是有序工作队列，不是某一组专属 SM；comm_stream 的名字不会把 NCCL kernel 自动送进 Copy Engine。前后两次跨 stream 依赖也不天然造成死锁：这个例子依赖方向始终向前，没有等待未来工作反过来完成过去工作的环。

仅用于同步时可以考虑 cudaEventCreateWithFlags(..., cudaEventDisableTiming)。生产代码还要检查 CUDA / NCCL 错误，并保证缓冲区与对象存活到使用结束。如果 GEMM 输出是 FP32，不能只把 AllReduce 的 dtype 写成 BF16 就期待 NCCL 自动完成类型转换。

event 完成标志由谁写，谁在等待？

API 保证event 表示被捕获的工作已完成，stream wait 约束后续工作。API 不要求某个 GEMM 线程在用户数组中写一个 done=true，也没有公开要求每个 event 必须独占一个 HBM 布尔变量。

公开机制驱动可以把 launch、完成等待、semaphore release / acquire 等命令写入 pushbuffer / GPFIFO。GPU 命令前端与调度机制在满足依赖之后才放行后继工作，所以等待本身不必先启动一个轮询 CTA。生产者执行路径在前序工作真正完成并满足存储顺序后发布同步值；仅解析到 launch 命令还不够。[18][20]

公开 UVM 代码提供了具体例子：uvm_hal_hopper_host_semaphore_release 先使用相关完成 / 内存屏障机制，然后配置 semaphore 地址、payload 和 release 操作；acquire 路径采用相应的计数比较条件。uvm_hal.c 还能看到 Blackwell 与 Hopper HOST HAL 的继承关系。源码中的 HOST / ESCHED 是 GPU 侧模块语境，不能翻译成“CPU 在等”。[18][19]

实现边界上述是“GPU 命令与硬件同步足以实现这一类依赖”的证据，不是 CUDA runtime 所有 event 实现的逐行还原。event 可能复用序列计数，标志位置也不必永远是 HBM；公开 semaphore 管理代码包含不同内存类型。具体轮询间隔、缓存位置或前端子模块分工，不应在没有证据时写死。[21]

在这个模型里，地址翻译模块负责让同步地址可访问；比较“值是否达到目标”、阻止或放行后继命令的是同步 / 调度机制。GMMU 并不是检查 event 语义的角色，FM / IMEX 更不负责每次本地 event 的放行。其他就绪 stream 仍可推进，但受到调度与硬件资源约束。

08 / COMPLETION SEMANTICS

allreduce_done 不保证所有卡同时退出 kernel

更准确的问题是：为什么本地 event 完成之后，本卡已经可以使用完整的归约结果？答案是 collective 的本地完成语义加上 stream 排序，而不是 event 再去检查一次所有 GPU。

从算法依赖推到本地 event

  1. 每个输出 chunk 要符合 AllReduce 语义，必须包含 communicator 中所有 rank 对应元素的贡献。
  2. Ring / Tree / NVLS 等算法通过各自的协议依赖确保这一点。尚未获得必要贡献的数据，不能被当作最终结果。
  3. 本 rank 的通信工作完成前，必须完成它所承诺的本地输出与相关传输 / 缓冲区生命周期义务。实际实现也会处理必要的 credit、可见性或传输排空。
  4. 本地 stream 排在这些工作之后的 event 才能达到完成状态。
  5. 等待这个 event 的本地消费者，因而可以使用该 rank 的 Y_i。

前两步来自 collective 语义与算法；后三步来自 NCCL stream 契约和 CUDA event 顺序。NCCL kernel 不需要拿到用户的 allreduce_done 句柄，也不负责替所有 OS 写同一个 event。[10][12][13][14][15]

一个允许发生的时间顺序

G0: 本地所有结果已到位 → 通信义务完成 → kernel 退出 → E0 完成 → Residual
G1: 本地结果已到位     → 仍在执行末尾工作 / 调度延迟 → kernel 退出 → E1 完成

E0 完成时，E1 可能尚未完成。
这不妨碍 G0 在其 stream 依赖下读取 Y0。

不同 rank 的 channel 进度、末尾收尾、调度和 event 发布时间都可以不同。“每个 rank 最终获得相同归约结果”不等于“所有 rank 的 kernel 在同一个时刻结束”。即使一个实现内部含有某些同步点，也不该把该实现细节升级成 API 对所有设备同时退出的保证。

如果业务确实需要知道全体已完成

// 伪代码：每个 rank 都执行。正常推理依赖链通常不需要这一全局确认。
cudaEventSynchronize(allreduce_done); // 先确认本 rank 的 GPU 工作完成
distributed_barrier();               // 再让所有 rank 报到
// 此时可以推断：所有参与该 barrier 的 rank 都已到达上述完成点。

单独在 CPU 上做 barrier，而不先确认本地异步 GPU 工作完成，通常只能证明各 CPU 到达某处，不能证明各 GPU 都已执行完。上述额外全局确认也会增加延迟，不能无条件塞进每个推理层。

以上结论讨论正常成功执行。NCCL 异步错误、通信故障或 abort 需要单独检查；不能因为某个 kernel 因错误退出，就宣称得到了正确的 AllReduce 结果。

普通 NCCL 管线中的逐步数据流

  1. Router：计算 expert ID 与 gate weight，记录 token 原始归属和 Top-2 分支。
  2. 计数与打包：按目的 rank 统计 count，计算 offset，把 token / metadata 放到可发送的连续布局；远端接收空间需要有匹配的大小或预分配容量。
  3. Dispatch：将打包后的数据送到 expert 所在 GPU。本地目的地不产生 NVLink 远端 payload，但仍可能有本地重排。
  4. 按 expert 重排：把同一 expert 的 token 聚到适合 grouped GEMM 的布局，保留回填索引。
  5. Expert 计算：执行各 expert 的 MLP，例如两路投影、SwiGLU 与输出投影。通信已经完成的部分是否可先计算，取决于框架支持的细粒度就绪协议。
  6. 反向通信：将各 expert 的输出送回原 token 的 owner，利用原路由 handle / 索引恢复关联。
  7. Combine：原 owner 按 gate weight 合并 Top-2 输出，得到自己的最终 token 输出。
y(t) = w(t,e₁) · Expertₑ₁(x(t)) + w(t,e₂) · Expertₑ₂(x(t))

这个求和只针对同一 token 被选中的专家结果，不是在所有 GPU 的所有 token 上做一次通用 AllReduce。

为什么不能直接把不等长数据套进固定 count 的 All-to-All？

NCCL 的 ncclAlltoAll 用一个 count 描述每个 peer 的固定元素数，而本例 C 的各项不相等。常见实现方式是按容量 padding，或使用 group 中匹配的 ncclSend / ncclRecv 组合表达不等长交换，并用额外协议准备接收大小。这里说的 All-to-Allv 是通信语义，不是在假设每个 NCCL 版本都有一个同名通用 API。[11]

// 概念伪代码：计数和 offsets 已可用，每条 send/recv 必须正确匹配。
ncclGroupStart();
for (peer : other_ranks) {
    if (send_count[peer] > 0)
        ncclSend(sendbuf + send_offset[peer], send_count[peer], dtype,
                 peer, comm, stream);
    if (recv_count[peer] > 0)
        ncclRecv(recvbuf + recv_offset[peer], recv_count[peer], dtype,
                 peer, comm, stream);
}
ncclGroupEnd();
// 本地分支单独处理；随后还需要 expert 布局与正确的消费依赖。

10 / MOE-SPECIALIZED COMMUNICATION

优化的是整个 EP 管线，而不只是换一个发送 API

普通 NCCL collective 是数据交换原语；MoE 专用库可以知道 token、expert、路由索引和返回合并的含义，因此能把通信与布局转换结合起来。比较时应同时观察额外 kernel、HBM 读写、同步边界和真正的远端字节，而不能只问“底层是否用了 NCCL”。

版本边界必须写清。2026-10-26 核对的 DeepEP main 文档为 V2.5 路线，使用 NCCL Gin、EPBuffer 等接口，并明确 EP dispatch / combine 仍使用 SM；不能把早期 NVSHMEM 依赖或某些路径的“零 SM”描述直接套用到当前 main。HybridEP 分支应单独看其实现，而不是把分支名当作 main 的别名。[27][28]

环节普通 collective 组成的基线EP 专用实现可以优化什么
路由与布局外部 kernel 计数、prefix、pack；通信后再 permute。融合路由元数据处理、搬运与 expert 布局，减少中间 buffer 和 HBM 读写。
变长长度准备 counts，可能做主机可见的长度同步或按容量 padding。用预分配容量、设备端计数和 handle 等组织协议；收益取决于下游是否也支持设备端动态长度。
数据搬运SM copy / NCCL kernel；也可能选到 CE 路径。TMA 或其他异步搬运把大段 payload copy 从逐元素线程指令中卸载，减少寄存器与发射压力。
就绪与计算常按整个 collective 的完成点启动后续 GEMM。按块、目的地或 expert 的就绪条件推进，减少不必要的全量等待；需要专门的消费协议。
返回与 combine反向交换后额外 unpermute / weighted sum。融合返回布局恢复、累加，或在允许的情况下先做局部 partial combine。
跨多个域应用决定层次交换结构。按 NVLink 域和网络分层组织转发；单个 NVL72 域中并不会仅因跨 OS 自动改走 RDMA。

这些是优化机会，不代表每个版本、每个配置都实现了所有行。HybridEP backend 中可以看到 shared-to-global TMA、bulk group 等待以及后续的发布次序和信号处理，说明它仍有 SM 协议代码，同时将大块搬运交给异步硬件。[29]

本例中，哪些字节真的能省？

原始 8-token 路由中，每个 token 的两个 expert 位于不同目标 rank，所以“同一目的 GPU 只发一份 token”的去重技巧不会直接减少这组 dispatch 的 224 KiB 远端向量。即便如此，融合 pack / permute、减少 staging 和同步仍可能有效。

如果把 t1 改成 E4、E5，它们都在 G2：专用协议可以只向 G2 传一份 16 KiB token，并携带两个 expert 的元数据，在 G2 本地展开；按 expert 分支分别发送的基线则会发送两份。返回阶段若语义允许，也可先在 G2 对该 token 的两个带权结果求和，再返回一份向量。这是条件性收益，不是 Top-2 MoE 永远减半。量化还会进一步改变字节数和精度行为，本文的 BF16 基线没有隐含这些优化。

怎么减少 SM 和同步开销？

SM 工作量：TMA 降低逐元素 load/store 和寄存器中转的需求；融合减少额外 kernel 与中间数据轮转；较少通信 CTA 可为 GEMM 留出资源。但协议计数、地址计算、barrier、ready / credit 发布仍要有人做，等待中的 CTA 也可能继续占用资源。

同步边界：细粒度就绪让部分 token 更早进入计算；设备端的路由、计数与布局处理可以减少 host round-trip；复用已知的布局或 handle 能减少重复工作。这些优化都保留必要的数据可见性和缓冲区复用协议，不是把所有同步删除。

NCCL 自己也有 CE / zero-CTA 路径

NCCL 2.28 引入了基于 NVLink 的 Copy Engine collective；后续版本扩展了相关路径。核对的 buffer registration 文档列出了适用于 NVLink / MNNVL 的 All-to-All、AllGather、Scatter、Gather 等纯搬运操作，并对 symmetric window 注册、CTA policy、驱动与版本提出条件。它们不需要用 SM 逐元素完成复制，但也不负责替模型自动融合 expert routing / GEMM。[25][26][30]

普通求和 AllReduce 不应从这个列表被推断成通用 zero-CTA。数据归约还需要相应计算或硬件能力；是否 offload、offload 到何处，应看实际算法。DeepEP 当前版本使用 NCCL 相关设备通信能力，也说明“NCCL vs DeepEP”更准确的对比是通用 collective 管线与 MoE 专用端到端管线。

评估时同时记录：token 规模、Top-k、expert 分布、精度、版本 / commit、SM 数量限制、接收布局、是否包含 pack / permute / combine、是否真实与 GEMM 重叠。没有这些前提，单个“带宽”或“占用 SM 数”很难形成可复用结论。

11 / ASYNC MOVEMENT & VISIBILITY

G0 用 TMA 写 G2：地址、数据和完成通知各走一条逻辑链

TMA 与 GPU Copy Engine 都能异步搬运数据，但它们的发起方式、内存端点和同步模型不同。TMA 的完成，不会自动变成远端应用理解的“这个 token 可以执行 expert GEMM”事件。

维度TMACopy Engine
典型发起者运行在 SM 的 CUDA 线程，通过异步 copy / tensor 指令。驱动 / stream 提交的复制命令；具体库可以封装更复杂操作。
典型数据端点global ↔ shared；还支持相应 shared / cluster 变体。global memory 间复制，包括满足条件的 peer 路径。
源 HBM → 远端 HBM通常需要先装入源 SM shared，再从 shared 发往远端映射；不是一条普通的 global→global TMA 指令。可直接承担复制，不要求用 SM shared 中转。
SM 参与发起、barrier、协议、必要的变换仍可能用 SM。纯复制可不分配通信 CTA；外围 pack / routing 仍可能用 SM。
完成方式依方向使用 mbarrier、bulk async-group 等；消费与发布还要满足内存模型。引擎完成路径和 stream / event 或库内部协议。
地址处理tensor map 可先从坐标、stride 产生 global 地址；GPU 翻译系统再处理 VA / peer 地址。复制请求同样需要正确映射、权限与硬件寻址路径。

TMA 的能力与同步定义见 CUDA async copy / PTX 文档；CE 在 NCCL 中的封装见其官方说明及源码。不能只看到 cudaMemcpyAsync 就不经检查地断言每一种大小、端点和实现都必定由某一个 CE 执行。[22][23][25][30]

逐步跟踪 G0 → G2 的一个 token

  1. 准备：G2 分配接收区与协议状态，G0 有可访问的远端映射 R₀₂。相关映射、权限和协议连接已建立；TMA 不负责自行向另一个 OS 申请内存。
  2. 装入 shared：G0 将本地 token 从 X₀ 装到 SM shared。对于相应 global→shared TMA 形式，事务完成字节与线程到达共同参与 mbarrier 条件，不能只用普通 CTA barrier 代替所有异步完成语义。
  3. 准备发出：若普通 SM 指令改写了待发送 shared 数据，要满足 generic / async proxy 之间规定的可见性次序。
  4. 远端 store：线程发出 shared→global 的异步 bulk store，目标使用 R₀₂。源端硬件地址处理将请求送到对应 fabric 地址，经 NVLink / NVSwitch 到达 G2；目标映射与存储系统完成对目标页的写入。
  5. 等待正确的完成层级：发起线程依据 bulk group 等待语义，区分“源 shared 已被读完”与“目标写入达到规定完成状态”。源 buffer 的复用与远端消费是两个问题。
  6. 发布 ready：协议代码在所需完成与 system-scope 次序之后发布序列号 / flag。对端使用匹配的可见性协议观察该通知，再消费自己的本地地址 Y₂。
  7. 消费与回收：G2 完成需要保护的读取后发布 credit / ack，允许 G0 在后续轮次安全复用对应槽位。

地址翻译由 GPU 硬件处理，驱动提前建好映射。远端落入 HBM 不要求 G2 的 SM 亲自执行一次“接收 memcpy”；但 G2 的 SM 是否正在轮询或执行计算，取决于上层消费协议。IMEX 不逐条中转 token，tensor map 也不是取代 GMMU 的第二套页表。

.read 为什么不能被当作远端 ready？

cp.async.bulk.wait_group.read 主要保证相关操作对源数据的读取已经完成，适合判断源 shared 是否可复用；它不等于“G2 的应用现在一定能消费目标数据”。不带 .read 的相应完整等待包含更强的目标写入完成语义，但跨线程 / 跨 GPU 的消费仍要遵循发布、获取与 proxy 的正确配对。PTX 的完成范围与可见性范围必须一起看。[23]

HybridEP 源码把 TMA store、bulk 等待和后续 signal / fence 组织在同一协议中，就是因为搬运完成与业务 ready 并不是同一层事件。不能将它简化成“硬件搬完就替 NCCL 自动设置了 CUDA event”。[29]

等待时，SM 能不能做其他计算？

可以有其他就绪 warp 或 kernel 推进，但前提是有可用资源。执行 TMA 的 CTA 可能仍保留 shared buffer、寄存器与线程槽；一个较大的 GEMM CTA 未必能挤进剩余空间。等待指令降低了主动轮询或复制的指令负担，不自动回收 CTA 资源。[24]

例如某种限制资源总量抽象为 100，驻留通信 CTA 使用 80，GEMM CTA 需要 40：即使通信 warp 大多在等，GEMM 也不能在同一 SM 共驻留。这只是资源约束的数字示例。把通信搬到 CE 可以避开这类 SM 占用，但它仍消耗 HBM、L2、互连与相关队列带宽，因此也可能拖慢计算。

13 / INFERENCE BEYOND ONE FABRIC

LLM 推理怎样跨越 scale-up 域？

Scale-up / scale-out 描述互连与系统边界；TP / PP / EP / CP / DP 描述模型怎样分工。两者不是同一组分类。一个请求可以在多个 NVLink 域之间协同完成推理。

这里的“域内”指受支持的 NVLink / NVSwitch fabric，“跨域”指通过 NIC 与 IB / RoCE 等网络连接不同域。NVL72 内的跨 OS 通信仍可属于 scale-up；不能仅凭节点数或机架外观判定。以下是逻辑布局示例，不把所有 NVL72 都设成同一种 OS 或 rank 配置。

方案分工对象跨域传什么推理中的主要代价
TP · 张量并行同一层的 head / 矩阵分块部分和或激活；AllReduce、ReduceScatter / AllGather 等逐层通信在关键路径上，小 batch decode 尤其受同步延迟影响
PP · 流水线并行不同层 / stagestage 边界的 hidden states流水线气泡、阶段不均衡；单请求仍依次经过各 stage
EP · 专家并行不同专家权重MoE token dispatch 与 expert output combine不规则 All-to-All、热点专家与尾部 rank
CP · 上下文并行同一请求的序列位置 / KV 区段KV 块、Q 或局部 attention 结果，依算法而异跨分区 Softmax / 输出合并与长上下文通信
PD 分离Prefill 与 Decode 的服务池KV cache、请求与布局元数据KV 交接时间、跨 TP 布局转换和池间排队
DP · 数据并行不同请求 / batch纯副本之间通常没有逐层 tensor collective负载和前缀缓存分布；DP attention + EP MoE 仍会通信

vLLM 支持多节点 TP，以及域内 TP、节点间 PP 的组合；PD 分离通过 connector 把 prefill 产生的 KV 交给 decode。CP 的 pass-KV / pass-Q 是不同的数据流选择，不能一概画成 NCCL AllReduce。[31][32][33]

例子：TP8 × PP4，DP=1

设模型有 64 层，4 个域各有 8 张 GPU。每个域承担 16 层，每层使用本域 TP8；一个 microbatch 依次走完四个域。逻辑 stage 边界共有 3 处，域内逐层 collective 留在 NVLink 中。具体哪个 rank 发送、是否按 shard 传输由框架布局决定，不能把图中的一条箭头理解成只有一张网卡承担全部数据。

32 GPU = TP 8 × PP 4 × DP 1
单个边界的逻辑激活量 = B × T × H × 每元素字节数

若 B=1、T=1、H=8192、BF16，逻辑边界张量为 16 KiB；若一次 prefill 处理 T=2048，则为 32 MiB。它们是逻辑张量大小，不是包含副本、协议和多跳的物理线速字节。PP 增加模型容量并可提升多请求吞吐，但不会让同一 token 同时穿过前后依赖的层。

真实部署与教学配置要分开

DeepSeek-V3 技术报告描述过跨节点的 prefill / decode 部署，其中 prefill 使用 32 GPU 的 EP，decode 使用 320 GPU 的 EP。这是论文披露的服务配置，用来说明 scale-out EP 已被实际采用；它不是运行模型的最低卡数，也不是对当前版本的推荐。[34]

选择并行方式时先明确目标：装下模型、装下长 KV、缩短单 token 延迟，还是提高给定延迟下的请求吞吐。增加 GPU 数不是目标本身。

14 / TOPOLOGY-AWARE OPTIMIZATION

跨域优化：减少慢链路上的字节和等待

相同的 collective，放在 NVLink 域内与跨 NIC 网络时，瓶颈可能完全不同。优先关注通信频率、重复数据、尾部等待和可重叠的独立工作。

并行方式可采用的优化必须一起考虑的限制
TP域内高频归约；跨域分层 collective、多 NIC 分片；融合后续 norm / residual小消息受启动 / 同步影响；大消息看有效带宽；融合需要真实依赖和内存顺序支持
PP均衡各 stage；microbatch / chunk 调度；与其他请求流水重叠切块越小，气泡可能减少，但 kernel 效率和通信摊销可能变差
EP按目标域去重转发、专家负载均衡、紧凑 token 布局、通信与 GEMM 重叠热点和最慢 rank 决定尾延迟；更多副本耗显存；量化有精度和 scale 元数据成本
CP按 prefill / decode 选择传 KV 或传 Q；局部计算与传输流水化必须合并 Softmax 统计量，不能直接平均各卡 attention 输出
DP / PD前缀缓存感知路由；独立调整两池容量；KV 分层、分块、异步交接热点副本排队可能抵消 cache 命中收益；交接必须匹配 dtype、层、位置与 TP 布局

TP：分层 AllReduce 的一个可手算模型

设 2 个域，每域 4 个 rank；每 rank 都有一个大小为 M 的部分和。先在域内 ReduceScatter，把 4 个部分和相加并切成 4 块。然后由两域中拥有同一块的 rank 做跨域 AllReduce，最后域内 AllGather 恢复完整结果。

域内 ReduceScatter → 同分片跨域 AllReduce → 域内 AllGather
每个跨域子组的缓冲区 = M / 4；全域仍有 4 个子组共同传输

这里减少的是每个跨域参与者负责的数据块，不是把整个系统必需的信息量凭空减少四倍。收益取决于 NIC 数量、GPU–NIC 亲和性、交换网络及并发映射。NCCL 会按可见拓扑和版本选择算法，这张图是正确的分层构造，不代表每次调用都采用该实现。网络内归约等能力也依赖受支持的交换硬件与插件。[10][13]

EP：为什么专用 dispatch 比“打包后普通 All-to-All”更有空间？

考虑同一 token 的 Top-4 专家全在另一个域：朴素按专家发送会跨域传 4 份激活；按目标域聚合的路径可以跨域传 1 份激活与路由信息，再在目标域展开为 4 个专家输入。若 H=8192、BF16，单 token 的激活部分可从 64 KiB 变为 16 KiB。该算例忽略路由元数据，并要求库支持这样的分层转发；若专家分散在四个域，则没有这项四倍去重收益。

Combine 方向是否先在目标域加权求和，再传回一个结果，取决于协议、数值精度和路由语义。不能仅凭 dispatch 去重就断言 combine 一定等量减少。

DeepEP 的不同分支和代际使用的通信后端不同；高吞吐与低延迟路径也面向不同消息规模。vLLM 提供多种 EP backend、专家负载均衡及 Dual Batch Overlap。选择时应记录库版本与 batch，而非只写“用了 DeepEP”。[27][28][35]

RDMA、TMA、GPU 发起通信都不自动等于零 SM。专用库可以少用线程搬运、融合打包 / 量化、缩小同步范围并重叠独立 batch；但 kernel 的 CTA 驻留、信号处理及代理进度仍要核对。对照第 11 章，区分 CE、TMA 与 SM 指令执行。

用测量区分带宽瓶颈与同步瓶颈

教学近似：T通信 ≈ 同步轮数 × 有效启动延迟 + 关键链路字节 / 有效带宽 + 尾部等待
T一步 ≈ T计算 + T通信 − 真正重叠的部分

这些式子用于定位问题，不是硬件性能预测器。至少同时记录 TTFT、每 token 延迟、吞吐、各 rank 尾延迟、collective 消息大小、NIC / NVLink 流量与通信 CTA 占用。只有 wall-clock 时间确实缩短，重叠才算有效；两个 stream 的时间线并排不代表没有争用。

15 / ATTENTION TENSOR PARALLELISM

Attention TP 默认切 head，但 KV 不一定能等分

常规一维 TP 把完整的 Q heads 分给不同 rank，并相应切分 QKV 与输出投影。每个 head 内部的点积和 Softmax 可以在本地完成；输出投影产生的部分和再跨卡归约。

下面使用行向量记法 Y = XW。ColumnParallelLinear 按输出特征分块，RowParallelLinear 按输入特征分块；PyTorch 的权重存储通常是 [out, in]，不要用文件中的矩阵外观反推数学切分方向。TensorRT-LLM 的并行策略与 vLLM 的 QKV / output projection 实现提供了可核对的实例。[36][37]

MHA：H=4096，32 heads，head_dim=128，TP4

各 rank 输入 X[T,4096] 相同。本地 Q、K、V 各含 8 heads；对完整可见序列计算 attention 后，拼接输出 Or[T,1024]。本地 WO,r[1024,4096] 产生 Sr[T,4096]，再求和得到 Y。

Y = concat(O₀,O₁,O₂,O₃) · WO = Σr=0..3 Or · WO,r

所以通常无须先 AllGather 四卡的 head 输出再乘完整 WO。拆成四个矩阵乘法后对结果求和，与完整线性代数表达式等价。使用 sequence parallel 等布局时，最后也可能用 ReduceScatter，让结果继续保持分片；本文先采用完整输出回到各卡的基准路径。

“切 head”“切 head_dim”“切序列”是三种不同的数据流

切完整 head：各卡独立得到自己的 scores 和 Softmax。切 head_dim：同一个 q·k 点积被拆开，需要先补齐或归约 scores，再做 Softmax。切序列：各卡处理不同历史位置，需要传递 KV / Q 或正确合并局部 Softmax 统计量。后两者都不能直接套用本节“只在输出处归约”的图。

MLA 也可以按完整 head 切计算，但其 cache 保存的是共享低维 latent，不是按 head 展开的独立 K/V。下一章把“head 被切了，cache 为什么没有变小”展开到每个张量。

16 / MULTI-HEAD LATENT ATTENTION

MLA TP：分 head 计算，复制压缩 cache

以 DeepSeek-V3 官方参考实现的 absorb 路径为基准：head 相关权重分片，共享的下投影权重与 latent cache 在 TP rank 上复制。这个例子解释一种可检查的实现，不代表所有生产后端都采用相同融合或缓存布局。

例子设 TP=8、单请求、单 token decode，不叠加 CP / sequence parallel。模型维度为 H=7168、128 heads、Query latent=1536、KV latent=512、非 RoPE Q/K=128、RoPE Q/K=64、V=128。以下缓存容量统一假设 BF16；这不代表官方配置的所有权重或实际 cache 都用 BF16。[38][39]

模块 / 张量每 rank 形状分片还是复制
输入 x[1,7168]复制
Query 下投影 WQA[7168,1536]复制，含相同的 latent RMSNorm
Query 上投影 WQB,r[1536,16×192]按 16 个本地 heads 分片
KV / RoPE key 下投影 WKVA[7168,512+64]复制；512 维部分做 RMSNorm
KV 上投影 WKVB,r[512,16×(128+128)]按本地 heads 分片
输出投影 WO,r[2048,7168]按本地 head 输出分块
历史 cacheC[L,512] 与 KR[L,64]每 rank 一份完整副本

1 · 本地生成相同的 latent，追加到本地 cache

各 rank 对同一个 x 用相同下投影计算 cQ[1536]、cKV[512] 与经过 RoPE 的 kR[64]。后两者追加到本地历史 cache；cQ 仅用于当前 query。这里以重复计算换取简单的数据依赖，不需要 G0 先算完再广播。所有下投影输出都不是“除以 TP 后的 latent”。

2 · 各 rank 生成自己的 16 个 Query heads

G0 负责 heads 0–15，G1 负责 16–31，依次到 G7 负责 112–127。本地上投影输出 [16,192]，每个 head 拆成 qCh[128] 与 qRh[64]，后者应用 RoPE。各 head 的权重不同，所以 query 不同；KV latent 共享并不使所有 head 等价。

3 · 把 K 上投影移到 query 一侧

设某个 head 的 K 上投影 WUKh 为 [512,128]。显式展开有 kCj,h = cKVj WUKh。利用矩阵乘法结合律：

qCh (kCj,h)T
= qCh (WUKh)T (cKVj)T
= q̃h (cKVj)T，其中 q̃h 是 512 维

每个 query head 先变成 512 维，再与本地 C[L,512] 点积，不必把所有历史 K 都展开到各 head。加上独立的 RoPE 项：

sh,j = α · [q̃h(cKVj)T + qRh(kRj)T]
ph,: = Softmax(sh,:)

α 保持模型的原定 scale：基础对应 1/√(128+64)，还可能含模型的长上下文调整。吸收后维度变为 512+64，不应因此改成 1/√576。因本卡有完整历史 cache 和完整本地 heads，scores / Softmax 无需跨 TP rank 归约。[34][38]

4 · 在 latent 空间加权求和，再做 V 上投影

zh = Σj ph,j cKVj ∈ ℝ512
oh = zh WUVh ∈ ℝ128

这是把 V 上投影从历史每个 token 的存储路径，移动到 attention 加权和之后。每个 head 有不同的概率与 WUVh，因此产生不同的输出。所谓“吸收”首先是线性代数重排，不保证实现一定预先生成巨大融合权重；参考代码仍有可见的局部矩阵乘法。

5 · 本地输出投影 → AllReduce → residual

Or = concat(本地 16 heads 的 oh) ∈ ℝ1×2048
Sr = OrWO,r ∈ ℝ1×7168
Y = AllReduceSUM(S0, …, S7)

每卡 Sr 的维度完整，但只含自己 16 个 heads 的贡献。NCCL 不必在这里搬运历史 cache，也不必 AllGather 原始 head 输出；它归约的是完整 hidden size 的部分和。参考实现用 RowParallelLinear 中的 dist.all_reduce 完成这一步。[38]

单请求单 token 的 BF16 归约缓冲区为 7168×2=14 KiB / rank。多个请求一起 decode 时按 batch 放大。本地通信完成后消费 Y，仍遵守第 8 章的本地完成语义：本 rank 的 event 并不是全体 kernel 退出确认。

为什么 cache 不随 TP 数量缩小？

每个本地 head 都需要完整 512 维 cKV。若把 latent 维切成 8 份，每张卡只能计算点积的一部分；必须重新收集 latent 或在 Softmax 前合并 scores。按序列切分则是 CP，需要分布式 Softmax 合并。这些方案可以设计，但改变了本节的数据流与通信成本。

每 token、每层、每 rank 的 BF16 cache = (512+64)×2 = 1152 B
单请求 L=32768：32768×1152 = 36 MiB / 层 / rank

TP8 与 TP16 都是 36 MiB / 层 / rank，但全组副本分别占 288 MiB 与 576 MiB。该数值只计有效缓存元素，不含页对齐、元数据、量化 scale、临时 buffer 或其他层。各卡要访问完整 cache，但实际 HBM 读取次数还取决于 kernel 的 tile 与复用策略。

交互计算：TP 变化时，哪些量会变化？

固定 DeepSeek-V3 维度、BF16 cache 与归约数据；每个请求每步生成 1 token。计算器给出逻辑容量，不估计性能。

与实际推理后端的边界

参考实现另有 naive 路径，显式保存本地 heads 的展开 K/V；不能拿该 cache 的形状解释 absorb 模式。实际 prefill 可以临时展开 K/V，decode 可以采用专门的 latent attention kernel，持久 cache 和临时工作区也应分开统计。扩大 TP 后，head 权重与部分计算减少，但共享下投影、cache 副本和归约仍存在；小 batch decode 不保证随 TP 线性加速。

另一种组合是 attention 使用 DP，让不同 rank 处理不同请求，并在 MoE 层通过 EP 共享专家容量。它可减少同一请求的 attention TP 协同，但要重新权衡 attention 权重副本、KV 放置和 MoE All-to-All。这里的“DP attention”不等于整模型的独立副本。[31][35]
