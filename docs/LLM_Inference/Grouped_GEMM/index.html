PART 1背景与动机

1.1 三种形态：单个 GEMM、Batched GEMM、Grouped GEMM

矩阵乘法 C = A × B 是所有深度学习计算的基石。当我们要算的不再是一对矩阵，而是一批矩阵乘法时，就出现了三种工程形态：

为什么不直接 for 循环 launch 多个 GEMM kernel？三个原因：

  • Launch 开销：每次 kernel launch 有数微秒的固定成本，MoE 模型一层几十个专家、几十层叠加后不可忽略；
  • SM 利用率：单个小组件可能只够填满几个 SM，串行执行时大部分算力闲置；合并成一次 launch 后，所有 tile 进入全局工作队列，SM 始终有活干；
  • 小矩阵效率：MoE 中很多专家只收到很少 token，单独 launch 的 GEMM 连 Tensor Core 的 tile 都填不满。

1.2 Batched GEMM 的两种内存组织

Batched GEMM 内部还分两种，区别在这批矩阵在显存里怎么摆：

一个贯穿本教程的视角：Batched 是 Grouped 的特例。当 grouped GEMM 的所有组形状相同时，per-group 的形状数组退化成一份，stride 数组退化成固定步长——理解这一点，后面看到 CUTLASS 用同一套 pointer-array kernel 同时覆盖两种场景就不会奇怪了。

1.3 应用场景

Batched GEMM 的典型场景是 Attention：每个 head 的 QKᵀ 和 softmax(·)V 就是一批形状相同的小 GEMM；此外还有小模型 ensemble、批量推理等。

Grouped GEMM 的主战场是 MoE（混合专家模型）。MoE 层里，router 把不同数量的 token 分给不同专家，每个专家是一次独立的 GEMM：

MoE 前向 = varlen-M Grouped GEMM；权重梯度反向 = varlen-K Grouped GEMM。CUTLASS 文档里称之为 "ragged M / K dimensions"。

1.4 为什么 Blackwell 上要重新设计

Hopper 时代已有 grouped GEMM，但它有两个结构性局限：

  • TMA 描述符在 host 侧预编码：每个 group 的 A/B 形状、基地址不同，要么为每组预生成描述符（组数多了以后参数空间爆炸），要么回退到非 TMA 的普通加载；
  • 调度基本静态：tile 到 SM 的映射在 launch 前确定，MoE 负载极度不均时（热门专家几千 token、冷门专家几个 token），大量 SM 空转。

Blackwell 为第一个痛点提供了直接的硬件武器：设备侧 tensormap 改写；而调度痛点的答案分两层——dense GEMM / stream-K 用上了 Cluster Launch Control（CLC） 动态调度，grouped GEMM 当前则仍走静态持久化调度（原因见 3.5 节）。再加上第五代 Tensor Core（tcgen05）和全新的 TMEM，整个 GEMM kernel 的骨架都值得重写。下一部分先讲硬件。

PART 2Blackwell 硬件底座

Blackwell（SM100 数据中心系列）为 GEMM 引入了四个关键新特性。理解它们是理解后面一切 kernel 设计的前提。

2.1 tcgen05.mma：第五代 Tensor Core 指令

Hopper 的 wgmma 需要整个 warpgroup（128 线程）协同发射，累加器摊在 128 个线程的寄存器里。Blackwell 的 tcgen05.mma（也叫 UMMA）则完全不同：

  • 单线程发起：一个 warp 里只要 1 个线程执行这条指令即可，其余线程/寄存器完全不参与；
  • 完全异步：发射后立即返回，硬件在后台执行，完成与否通过 mbarrier 查询；
  • 累加器落 TMEM：结果写进专用的 Tensor Memory，不占寄存器。
概念对比（伪代码）pseudo
// Hopper wgmma：整个 warpgroup 参与，累加器在寄存器
warpgroup_arrive();
wgmma(acc_regs, smem_A, smem_B);   // 128 线程的寄存器共同持有 acc
warpgroup_commit(); warpgroup_wait();

// Blackwell tcgen05：单线程发射，累加器在 TMEM
if (elect_one_thread()) {
  tcgen05.mma(tmem_acc, smem_A, smem_B);  // 异步，立即返回
  tcgen05.commit(mbar);                    // 完成后敲 mbarrier
}

tcgen05 还有两个重要维度：

  • 1-SM vs 2-SM（cta_group::1 / ::2）：2-SM 模式下，cluster 中相邻的一对 SM 合作执行同一条 MMA 指令，MMA tile 可达 256×256；B 矩阵由两个 SM 的 SMEM 各存一半，等效 SMEM 容量与加载带宽翻倍；
  • SS vs TS：操作数来源可以是 SMEM（SS，A、B 都经 TMA 进 SMEM）或 TMEM（TS，A 已在 TMEM 中）。主流路径是 SS。

2.2 TMEM：Tensor Memory 与累加器双缓冲

TMEM 是 Blackwell 每个 SM 上新增的 256 KB 片上存储：128 行（lane）× 512 列，每格 32 bit。它与寄存器堆完全分离，直接连着 Tensor Core。

配套的指令与机制：

  • tcgen05.ld / tcgen05.st：TMEM ↔ 寄存器的数据搬运（epilogue 用它读累加结果）；
  • tcgen05.alloc / dealloc：TMEM 是按列分配的资源，CTA 启动时申请、退出前归还；
  • 累加器流水线（accumulator pipeline）：MMA warp 和 epilogue warp 之间通过 mbarrier 传递 TMEM stage 的"所有权"。

2.3 TMA 增强：设备侧改写 tensormap

TMA（Tensor Memory Accelerator）用一个 128 字节的描述符（tensormap）描述全局内存中张量的形状、stride、基地址和 swizzle 模式，之后一条指令就能搬运一个多维 tile，无需逐线程算地址。

常规 GEMM 中，tensormap 在 host 侧用 cuTensorMapEncodeTiled 编码好，随 kernel 参数传入。但 grouped GEMM 每组形状和地址都不同——Blackwell 给出的答案是允许 kernel 在设备侧修改 tensormap：

设备侧 tensormap 改写（伪代码，对应 PTX tensormap.replace）pseudo
// 持久化 CTA 切换到新 group 时
tensormap.replace(smem_desc, global_address, ptr_A[g]);  // 换基地址
tensormap.replace(smem_desc, global_dim[0],  K[g]);      // 换形状
tensormap.replace(smem_desc, global_dim[1],  M[g]);
tensormap.replace(smem_desc, global_stride[0], stride_bytes);
fence.proxy.tensormap();       // 让 TMA 引擎看到修改（关键！）
// 之后即可照常 tma.load，硬件按新描述符取数
常见坑

改写 tensormap 后必须执行 fence.proxy.tensormap，否则 TMA 可能读到旧描述符——这类 bug 表现为结果偶发错误，极难排查。2-SM 模式下还要注意 cluster 内两个 CTA 的描述符一致性。

2.4 CLC：Cluster Launch Control 动态调度

传统 GPU 调度是静态的：grid 里每个 CTA 干什么，launch 时就定了。Blackwell 的 CLC 引入了硬件级动态调度：一个跑完的 CTA 可以向硬件"领取"新工作，无需回 host、无需重新 launch。基于它，CUTLASS 实现了：

  • 持久化 tile scheduler：launch 与 SM 数量相当的 CTA，每个 CTA 循环领取 tile 直到工作队列清空；
  • Stream-K 负载均衡：把 K 维也切开分摊，解决尾波效应。
落地范围

CLC 目前用在 dense GEMM 与 stream-K（PersistentTileSchedulerSm100）：scheduler warp 作为生产者发 clusterlaunchcontrol.try_cancel 查询，MMA / load / epilogue warp 作为消费者取结果，流水线深度 3 以隐藏查询延迟。grouped GEMM 当前不在其列——它用的是静态持久化调度，原因见 3.5 节。

PART 3核心实现难点

3.1 Batched GEMM：最简单的多 GEMM 路径

先看最省心的情况。Strided batched GEMM 中，所有矩阵形状相同、在显存中等间距排布，因此 batch 维可以直接作为张量的第 4 维写进 TMA 描述符——host 编码一次，device 完全不用改：

Strided batched：batch 只是 layout 的第 4 维cpp
// (M, N, K, L)：L = batch 数；stride 数组里第 4 项是 batch_stride
auto layout_A = make_layout(make_shape(M, K, L),
                              make_stride(lda, 1, stride_batch_A));
// TMA 描述符编码一次即可覆盖所有 batch —— 无任何设备侧改写

调度上也没有难点：grid 的 z 维天然对应 batch，每个 CTA 的任务在 launch 时就确定。这就是为什么选型时能用 strided batched 就不用指针数组，能用 batched 就不用 grouped——每向上一层，descriptor 改写和调度的开销都在递增。

3.2 Grouped GEMM 难点一：指针数组与 per-group 元数据

Grouped GEMM 的一切输入都变成了"数组"：

数据普通 GEMMGrouped GEMM
问题形状单个 (M, N, K)设备侧数组 problem_sizes[g]
A / B / C / D 地址单个指针指针数组 ptr_A[g] …
Stride一组stride 数组 stride_A[g] …
α / β 缩放两个标量可选 per-group 数组

CUTLASS 3.x 用专门的类型表达这一切：

Grouped GEMM 的问题描述（example 75 风格）cpp
using ProblemShape = cutlass::gemm::GroupProblemShape<Shape<int,int,int>>;  // 每组 (M,N,K)

typename Gemm::Arguments args{
  cutlass::gemm::GemmUniversalMode::kGrouped,
  {groups, problem_sizes_dev, nullptr},              // 组数 + 设备侧形状数组
  {ptr_A, stride_A, ptr_B, stride_B},                  // mainloop：指针数组 + stride 数组
  {fusion_args, ptr_C, stride_C, ptr_D, stride_D},     // epilogue
  hw_info, scheduler
};

Host 侧的典型做法是先打包再指认：把所有组的 A 连续拷进一个大内存池 block_A，记录每组偏移 offset_A[g]，最后填指针数组 ptr_A[g] = block_A + offset_A[g]。MoE 场景下，"打包"这一步天然由 router 的排序+前缀和完成：

MoE 前向的 host 侧准备（Python 伪代码）python
expert_of = router.topk(X)                    # 每个 token 的专家号
order     = argsort(expert_of)                # token 按专家排序
counts    = bincount(expert_of)               # 每个专家的 token 数 = M[g]
offsets   = exclusive_prefix_sum(counts)

X_packed  = X[order]                          # 连续内存池（gather）
for g in range(num_experts):
    problem_sizes[g] = (counts[g], N_ffn, K_hidden)
    ptr_A[g] = X_packed + offsets[g] * K_hidden
    ptr_B[g] = W1[g]                          # 专家权重，天然指针数组
    ptr_D[g] = Y_packed + offsets[g] * N_ffn

3.3 难点二：动态形状如何映射到固定大小的 MMA tile

这里藏着 grouped GEMM 最本质的一个矛盾：tcgen05.mma 的 tile 形状是编译期固定的（如 128×256×64 或 256×256×128），而每组的 (M, N, K) 是运行期才知道的任意整数。弥合这道鸿沟靠三层机制：

① Tile 网格量化：向上取整

调度器为每组计算 tile 数，把 (g, tile_m, tile_n) 展平进全局工作队列：

tile 数量化（伪代码）pseudo
// 每组独立量化，M=200、TILE_M=128 → 2 个 M tile（第 2 个只有 72 行有效）
tiles_m[g] = ceil_div(M[g], MMA_TILE_M);
tiles_n[g] = ceil_div(N[g], MMA_TILE_N);
k_tiles[g] = ceil_div(K[g], MMA_TILE_K);   // K 残块：TMA 读越界补 0，累加仍正确

以 M=200、N=300 的组为例，在 128×128 tile 下产生 2×3 个 tile，其中 4 个是残块 tile（boundary tile）：

② 越界读：TMA 自动补 0

这正是 3.4 节改写 tensormap 的隐藏红利：描述符里的 global_dim 已经是这组的真实形状，TMA 读取越界区域时自动返回 0。0 是矩阵加法的中性元——K 维残块补 0 后累加结果依然正确，残块中无效行的 A 补 0 后算出的行本身就是 0，反正最后也不会被写回。MMA warp 完全不需要知道自己正在算残块。

③ 越界写：掩码丢弃

epilogue 的 TMA store 同样以改写后的 D 描述符形状为界，无效行/列根本不会写回显存；若使用非 TMA 的写出路径，则退回逐元素谓词化（predicated store）。

代价：量化浪费。上面 M=200 的例子实际算了 256 行（MMA 利用率 78%）；而 M=4 的小专家在 128 行 tile 下只有 3% 的利用率——残块 tile 消耗的 MMA 周期和完整 tile 一模一样。这个数字是 grouped GEMM 效率分析的核心，5.2 节的缓解手段（token 排序、合并小专家）都是围绕它展开的。

对齐提醒

每组基地址仍须满足 TMA 的 16 字节对齐（FP8 下通常 K 方向 128 元素对齐）。host 侧打包内存池时，各组 offset 要按对齐要求向上取整，否则 can_implement 会直接拒绝。

3.4 难点三：设备侧 TMA descriptor 改写

这是 grouped GEMM 在 Blackwell 上最关键的一个机制，也是 example 75 展示的核心新特性。流程如下：

细节要点：

  • tensormap 的修改发生在 SMEM 中的描述符副本上，改完用 fence.proxy.tensormap 对 TMA 引擎可见，再通过 cp.async.bulk.tensor 使用该副本；
  • 1-SM 与 2-SM 的差异：2-SM 模式下 cluster 内两个 CTA 都要看到一致的描述符，fence 与同步的范围扩大到 cluster；

3.5 难点四：设备端调度与负载均衡

逻辑上，所有 group 的输出 tile 被展平成一个全局工作队列，每个队列项是 (group_id, tile_m, tile_n)：

这里要澄清一个容易误解的事实：当前 CUTLASS 的 grouped GEMM 并没有使用 CLC。它的调度器是 PersistentTileSchedulerSm100Group——一个 SM90 风格的静态持久化调度器：launch 时开尽可能大的 grid，每个 CTA 用 blockIdx 经设备侧公式（遍历各组 tile 计数）自行算出 tile 序列，没有硬件工作队列参与。

为什么不用 CLC？CUTLASS 源码注释给出了直接答案：grouped GEMM 的常见用法里 problem shapes 只在设备侧，launch 时不知道总共有多少 tile；而 CLC 返回的 ClcID 是线性化坐标，必须知道 grid 几何才能映射回 (g, tile_m, tile_n)。源码同时留好了退路：如果 host 侧拿得到形状（部分推理框架可以做到），就能算出 grid 形状并改用 CLC 查询——调度器接口（CLCResponse、fetch_next_work 等）刻意与 CLC 版保持一致，kernel 主体两种调度器通用。CLC 目前真正的落地场景是 dense GEMM 与 stream-K（2.4 节）。

静态调度的代价是对"SM 被其他工作占用"不敏感、组间大小悬殊时尾波明显。作为补偿，grouped 调度器把 per-group 的 cluster swizzle 启发式放在设备侧计算（按各组形状分别选择 swizzle 大小），并同样支持 preferred / fallback cluster shape：优先按 2×1 等偏好形状启动 cluster，硬件资源不足时回退到更小形状，保证 kernel 总能启动。

4.3 Host 侧流程

example 75 的 host 代码示范了标准做法，MoE 工程实现也基本是这个套路：

host 侧：连续内存池 + 偏移表 → 指针数组cpp
// 1. 决定每组形状（MoE 中来自 router 的 counts）
problem_sizes_host[g] = {m_g, n_g, k_g};

// 2. 计算偏移，分配一整块连续显存
offset_A[g] = 累加(m_g * k_g);
block_A.reset(total_elements_A);   // 内存池

// 3. 填指针数组与 stride 数组，拷到设备
ptr_A_host[g]    = block_A.get() + offset_A[g];
stride_A_host[g] = make_cute_packed_stride(StrideA{}, {m_g, k_g, 1});
ptr_A.copy_from_host(ptr_A_host.data());

// 4. 组包 Arguments → can_implement → workspace → initialize → run
auto args = typename Gemm::Arguments{
    cutlass::gemm::GemmUniversalMode::kGrouped,
    {groups, problem_sizes.get(), nullptr},
    {ptr_A.get(), stride_A.get(), ptr_B.get(), stride_B.get()},
    {fusion_args, ptr_C.get(), stride_C.get(), ptr_D.get(), stride_D.get()},
    hw_info, scheduler};

4.4 Kernel 主循环剖析

把前面所有机制串起来，一个持久化 CTA 的生命周期是这样的（伪代码，省略了 pipeline 状态管理细节）：

持久化 CTA 主循环（伪代码）pseudo
// ── CTA 启动，一次初始化 ─────────────────────────
tmem_alloc();                          // 申请 TMEM 列
init_pipelines();                      // mainloop pipeline + accumulator pipeline

while (tile = scheduler.next()) {      // 静态持久化调度取下一个 tile (g, tm, tn)

  // ── 跨组时改写 tensormap（见 3.4）─────────────
  if (tile.group != cur_group) {
    update_tensormaps(ptr_A[g], M[g], K[g], ptr_B[g], N[g]);
    fence_proxy_tensormap();
    cur_group = tile.group;
  }

  // ── mainloop：TMA producer 与 MMA warp 并行 ───
  if (warp_role == producer) {
    for (kt in k_tiles) {
      ab_pipeline.producer_acquire(state);
      tma_load(A_tile → smem[stage], mbar);
      tma_load(B_tile → smem[stage], mbar);
    }
  } else if (warp_role == mma) {
    for (kt in k_tiles) {
      ab_pipeline.consumer_wait(state);
      if (elect_one()) tcgen05.mma(tmem_acc, smem_A, smem_B);
      ab_pipeline.consumer_release(state);
    }
    tcgen05.commit(acc_mbar);          // 通知 epilogue：这个 stage 满了
  }

  // ── epilogue：TMEM → 寄存器 → 全局内存 ────────
  if (warp_role == epilogue) {
    acc_pipeline.consumer_wait();
    rmem = tcgen05.ld(tmem_acc);       // 读累加器
    out  = alpha[g] * rmem + beta[g] * load_C(tile);
    tma_store(out → D[g] 对应 tile);
    acc_pipeline.consumer_release();   // 归还 TMEM stage 给 MMA
  }
}
tmem_dealloc();
阅读源码的路标

看 kernel 层代码时，按这三个关键词定位：GroupProblemShape（调度与组边界）、tensormap（设备侧改写）、AccumulatorPipeline（TMEM 双缓冲）。其余结构与 Blackwell dense GEMM 完全一致。

4.5 Block-Scaled 变体：NVFP4 / MXFP8 的 Grouped GEMM

examples/75_blackwell_grouped_gemm/ 下还有 75_blackwell_grouped_gemm_block_scaled.cu，面向 FP4/FP8 块缩放格式（NVFP4 每 16 个元素一个 scale factor，MXFP8 每 32 个）：

  • scale factor（SF）张量本身也指针数组化，随 group 切换；
  • SF 有严格布局要求（按 128×4 的 atom 组织），对齐约束比普通 FP8 更苛刻；
  • CUTLASS 从 3.8 起为 block-scaled 数据类型分别提供"支持 / 不支持指针数组"两种 mainloop——grouped 必须选前者。

PART 5选型与调优

5.1 决策树

其余配置经验：

  • Cluster shape：优先 2×1（2-SM 模式必须），配合 preferred/fallback 机制；
  • Stage 数：交给 StageCountAutoCarveout，它会扣除 epilogue 的 SMEM 占用后自动算最大 stage 数；
  • 调度策略：KernelScheduleAuto 能自动挑，但官方文档建议生产环境显式指定直接调度策略，行为更可预测。

5.2 MoE 场景的特有问题

  • 小 M group 的 tile 浪费：M=4 的专家也要占一个 128 行的 MMA tile，利用率 3%。缓解：token 排序后把极小专家合并计算，或对它们退回普通 GEMM；
  • B 矩阵加载是流量大头：A（激活）可被同组内多个 tile 复用，但每组权重 B 独享且很大。自研 kernel 常用手段：加宽 TMA box（一次搬两个 K tile）、跨 K-tile 共享 B stage、给 B 加 L2 cache policy；
  • varlen-K 尾部：权重梯度 GEMM 中 K 随组变化，注意新版 CUTLASS 已放宽 K 必须整除 tile K 的限制，并支持 K=0 的空 group。

5.3 测量与验证

用 CUTLASS profiler 扫 grouped GEMM 配置bash
$ ./cutlass_profiler --operation=GroupedGemm --help

# example 75 自带的两种用法
$ ./75_blackwell_grouped_gemm --m=2048 --n=2048 --k=2048 --groups=10
$ ./75_blackwell_grouped_gemm --benchmark=problems.txt   # 每行: 序号 MxNxK

性能分析时建议按 per-group GFLOP/s 统计（example 75 已内置），再对照 roofline：小 M 的组必然落在带宽受限区，这是物理规律而非 kernel 缺陷。正确性验证走 cutlass::reference::device::Gemm 逐组对比的常规流程。

5.4 生态对照（选读）

  • CuTe DSL（Python）：CUTLASS 4.x 的 Python 前端可以写同款 Blackwell grouped kernel，迭代更快，适合研究；
  • SonicMoE / QuACK：Tri Dao 团队在 CuTe DSL 之上为细粒度 MoE 设计的 kernel 库，其 varlen-M/varlen-K 抽象与本教程完全一致；
  • TRT-LLM / vLLM：生产推理框架中的 MoE grouped GEMM 工程实践，可在它们之上观察真实负载分布对调度的影响。

C. 常见坑

  • 改写 tensormap 后漏掉 fence.proxy.tensormap → 偶发性错误结果；
  • cluster shape 不支持时未配 fallback → kernel 无法启动；
  • TMEM 申请超出 512 列 → 编译期或 launch 失败，注意 epilogue 也要占列；
  • 把 CTA tile 当成 MmaTileShape 传给 builder → 形状不匹配报错；
  • group 数很大时 host 侧指针数组拷贝未批量化 → launch 前延迟升高。
