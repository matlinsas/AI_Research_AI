CDNA4 的 LDS 带宽需求

CDNA4的256 byte/CU/cycle LDS读带宽，需要依靠寄存器复用来供应低精度Matrix Core。 64×64 wave tile通常已有读带宽余量；128×128更省读取，但寄存器占用更大。

2. 每条MFMA都重新加载A/B，需要多少带宽？

一条m×n×k的MFMA，如果A/B每元素均为s byte、执行周期为t，则四个Matrix Core的总供数需求为：

LDS读需求 = 4 × k × (m+n) × s / t
输入类型16×16输出：尺寸、周期 → 带宽32×32输出：尺寸、周期 → 带宽
FP16 / BF1616×16×32，16周期 → 51232×32×16，32周期 → 256
FP816×16×128，32周期 → 51232×32×64，64周期 → 256
FP6，紧凑16×16×128，16周期 → 76832×32×64，32周期 → 384
FP4，紧凑16×16×128，16周期 → 51232×32×64，32周期 → 256
INT816×16×64，16周期 → 51232×32×32，32周期 → 256

带宽单位均为byte/CU/cycle。周期是单wave指令模型；FP8采用满速F8F6F4路径。FP6按0.75 byte/元素、FP4按0.5 byte/元素打包，暂不计MX scale。CDNA4 ISA

例如FP16的16×16×32：

A+B = (16×32 + 32×16) × 2 = 2,048 byte / wave LDS读需求 = 4 × 2,048 / 16 = 512 byte/CU/cycle

512超过LDS的256峰值。 如果每条MFMA都重新读取A/B，仅LDS读取就会将这一方式的算力上限限制在约50%。

3. 扩大wave tile，用寄存器复用降低需求

Wave tile是一个wave连续执行多条MFMA后负责的输出块，不等于单条MFMA的尺寸。 设它为Mw×Nw，A/B各加载一次后在多条指令间复用：

LDS读需求 = P / 2 × (sA/Nw + sB/Mw) 平方tile、A/B同类型：LDS读需求 = P × s / Mw

P是整个CU的目标算力，已包含四个Matrix Core，不再乘4。

每wave输出tileFP16 / BF16FP8 / INT8FP6FP4
16×16512512768512
32×32256256384256
64×64128128192128
128×12864649664

单位：byte/CU/cycle；未计scale。假设每个wave分别读取自己的A/B，没有跨wave的免费multicast。

64×64时，FP16 / FP8 / FP4降到128，FP6降到192。 128×128还可以继续减半。因此，wave内的寄存器复用是喂满Matrix Core的关键。

4. VGPR / AGPR能容纳这么大的tile吗？

FP32累加时，C/D原地更新只计一份。以每lane的32-bit寄存器数计算：

Rc = Mw × Nw / 64 Rab = Kr × (Mw×sA + Nw×sB) / (64×4) Rtotal ≈ Rc + 2×Rab + 16

示例选择FP16的32×32×16 MFMA：Kr＝16，A/B采用完整双缓冲，另预留16个普通VGPR/lane。

Wave tileC累加器A/B双缓冲＋其他总寄存器/laneRF限制waves/SIMDLDS读需求
32×321632488256
64×6464481124128
128×12825680336164

64×64用112个寄存器/lane，可将读取需求降到峰值的一半；128×128用336个，通常只能驻留1 wave/SIMD。

相同假设下，64×64的满速FP8、FP6、FP4分别约需144、128、112个寄存器/lane，容量也可行。

这些是示例预算，不是编译结果；未计scale寄存器。128×128已用满256 AGPR/lane，这是“C全放AGPR”策略的边界，不是所有混合分配方案的绝对上限。

5. 还要给scale和LDS写入留余量

如果每32个元素的1-byte scale也从LDS紧凑加载，64×64 wave tile的读需求为：

输入格式A/B数据＋scale：byte/CU/cycle
MXFP8132
MXFP6200
MXFP4136

再看一个完整FP16例子：四个wave按2×2排列，每wave算64×64，workgroup算128×128，LDS每级缓存Kb＝64。

  • LDS逻辑双缓冲容量：64 kB。
  • 满算力时的A/B读取：128 byte/CU/cycle。
  • 下一批A/B写入LDS：另需64 byte/CU/cycle。

Kr是寄存器中的活跃K片段，Kb是LDS缓冲深度，两者不同。256是峰值读带宽，不能理解为同时还能免费追加任意写带宽。 Bank conflict、读写竞争和调度都可能降低有效供数。

Scale粒度见CDNA4 ISA；LDS读带宽见CDNA4 白皮书。

6. 分析结论

64×64 wave tile是一个兼顾LDS带宽与寄存器占用的分析起点。
它把多数低精度格式的读取需求降到128 byte/CU/cycle，FP6为192；寄存器容量也允许实现。

128×128更省LDS读取，但显著减少可驻留wave数。是否更快，需要验证独立累加链和指令级并行度能否维持MFMA利用率。这里给出的是容量与带宽模型，不是达到峰值的性能保证。

7. VGPR / AGPR的带宽需求

扩大wave tile主要降低LDS→VGPR流量；矩阵指令仍要消费A/B和累加器。 下面把寄存器容量问题继续拆成带宽问题。

本节数字是逻辑操作数流量，不是已公布的VGPR物理峰值。 所查AMD白皮书和ISA未给出足以统一核算的RF阵列总读/写峰值。容量、SIMD宽度、源操作数个数，均不足以倒推出全部端口带宽；因此这里不计算“VGPR峰值利用率”。

7.4 扩大tile，为什么没有把A/B寄存器读取也同比降下来？

固定32×32×16 FP16 MFMA和目标算力时，wave tile从32×32扩大到64×64、128×128，LDS→VGPR输入写入依次是256 → 128 → 64 byte/CU/cycle；但逐条MFMA累计的A/B逻辑读仍是256。一个VGPR片段可以少加载，却仍被多条MFMA消费。

同理，C/D不必回LDS，不代表RF阵列一定不读写：本例C读、D写逻辑量各512。实际阵列流量还取决于缓存、转发及硬件实现，不能从AGPR名称或共享容量推断。

7.5 结论

64×64 FP16示例：输入写128；A/B读256；C读512；D写512 byte/CU/cycle。
LDS复用、RF容量和RF供数是三个不同约束。寄存器容量足够、LDS也有余量，仍不能单凭这两项证明MFMA能满速。

实际优化应检查编译出的矩阵形状、VGPR/AGPR分配、输入复用与spill，再用微基准或性能计数器定位瓶颈。本文给出可复算的逻辑供数预算；物理RF峰值保留为未知。
