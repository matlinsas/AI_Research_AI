Mental model

先抓住一条主线

主机侧把“张量长什么样”写进 TensorMap；kernel 每次只给出“要哪一块”的坐标；TMA 引擎负责地址遍历、边界与布局，并通过 mbarrier 或 bulk-group 报告完成。

这把大量重复的整数地址计算、分支和 per-thread 拷贝，从 SM 指令流转移到专用异步数据路径。真正的收益通常来自整个流水设计，而不是孤立地替换一条 load。

Three-part contract

硬件／软件接口的三个部分

1
TensorMap：静态结构

维度、全局步幅、box、遍历步幅、边界填充、swizzle／interleave。

2

一次选择 tile／im2col 区域，并指定 SMEM、mbarrier、cluster mask 等。

3

load 以 transaction bytes 记账；store／reduce 以 bulk-group 退休。

01 · Tiled rank：为什么需要 1D、2D、3D、4D、5D

rank 不是性能档位，而是“一次地址计算要保留多少根逻辑坐标轴”。

查看背景章节 ↓

先建立选择原则

把只在一个 tile 内遍历的轴保留给 box，把需要在多次 TMA 之间选择 batch／head／group 的轴保留为坐标。若软件本来就要在 kernel 内拼出多维坐标，却先把张量压平成 2D，就会重新引入除法、取模和 stride 合成。

rank = 逻辑张量坐标轴数，不是 SMEM 维数，也不是每次搬运的有效轴数。 高 rank box 的外层维度可以取 1；但“可以压成低 rank”不代表“应该压”，关键看压平是否把索引运算重新推回 SM。

为什么要有多个宽度

不同 dtype、K／MN-major 和 tile 形状对应不同 SMEM canonical atom。128B atom 不能无条件套到 32B 或 64B 的连续方向：描述符可能无法创建，或者 GMMA descriptor 对同一地址的解释不同。较小模式则让窄 atom 仍能在搬运阶段完成 bank 分布变换。

01

Tiled 多维 load／store

Bounding Box · 动态坐标 · 1D～5D

解决什么

GEMM、Attention 等 kernel 只需要全局张量中的一块，但每轮都为每个线程计算地址、处理行跨度和多维层级，会让主循环充满整数运算与控制指令。

1功能定义

Tiled mode 用 TensorMap 描述 1D～5D 全局张量，以及一个最多同样维数的 boxDim。每次指令提供逻辑坐标，选择全局张量中的一个 box，在 global memory 与 shared memory 之间异步搬运。

  • globalDim／globalStrides：全局张量的逻辑形状与跨维字节步幅。
  • boxDim：单次 TMA 操作覆盖的逻辑块，也就是常说的 tile／bounding box。
  • 指令坐标：按元素索引选择块的位置；描述符复用，坐标随 mainloop 改变。

2PTX 指令

LOAD / STORE · 示意形式，省略可选修饰符 
// Global → Shared：到达后由 mbarrier 记账
cp.async.bulk.tensor.2d.shared::cluster.global
  .mbarrier::complete_tx::bytes
  [smem_tile], [tensor_map, {x, y}], [mbar];

// Shared → Global：由 bulk-group 跟踪
cp.async.bulk.tensor.2d.global.shared::cta.bulk_group
  [tensor_map, {x, y}], [smem_tile];

将 .2d 换为 .1d/.3d/.4d/.5d 即对应不同维数。坐标不是任意字节指针算术，而是 TensorMap 所定义坐标空间中的元素位置。

软件给出什么

02

OOB 填充与 traversal stride

Zero-fill · OOB-NaN · 元素遍历间隔

解决什么

张量尾块越过边界、卷积 padding，以及 dilation／下采样等规则访问，本来都需要额外分支或地址变换。TMA 把其中适合描述符表达的部分下沉到搬运引擎。

1功能定义

OOB（out-of-bounds）定义 box 与全局张量边界相交时的行为：load 可将越界位置填零，或使用特殊 OOB-NaN 填充。traversal stride（TensorMap 的 elementStrides）定义 box 内相邻逻辑元素在全局张量坐标中的遍历间隔。

最容易混淆：traversal stride 不是 global memory 的行间距。globalStrides 决定“跨维时内存怎么走”，elementStrides 决定“逻辑遍历每次跨几个元素”。

2PTX 指令

OOB 和 traversal stride 都不是新的 cp 助记符，而是 TensorMap 的属性；主指令仍然是 tiled／im2col 形式的 cp.async.bulk.tensor。

TENSORMAP FIELDS · 概念视图，不是构造函数签名 
tensor_map.globalDim      = {W, H, C, N};
tensor_map.globalStrides  = {stride_H_bytes, ...};
tensor_map.boxDim         = {box_W, box_H, box_C};
tensor_map.elementStrides = {step_W, step_H, step_C};
tensor_map.OOBFill        = ZERO // 或特殊 OOB-NaN 模式

3使用场景和原理

  • 尾块：当 M／N／K 不是 tile 整数倍，box 仍可按统一形状发起，越界输入填零，计算路径保持规则。
  • 卷积边界：输入激活 tile 覆盖 halo；padding 区域由边界机制处理，避免单独构造零填充输入。
  • 膨胀／规则抽样：遍历间隔大于 1 时，box 的逻辑位置按间隔映射回全局张量。

03

Shared-memory swizzle

None · 32B · 64B · 96B · 128B · atomicity 子模式

解决什么

规则二维 tile 直接线性放入 SMEM，可能让 GMMA／计算线程的访问落到相同 bank，也未必匹配计算指令要求的布局。逐线程重排又会抵消异步搬运的收益。

1功能定义

Swizzle 是 TMA 写入 SMEM 时执行的地址重排。TensorMap 声明模式，TMA 引擎在搬运过程中完成；后续计算必须使用与之匹配的 SMEM layout 解释数据。

模式包括 None、32B、64B、96B、128B；128B 还定义了 atomicity 子模式。它们描述的是 共享内存内部布局，不是 global tensor 的维度，也不是 cache line 交织。

2PTX 指令

PTX 拷贝指令不需要额外的 “swizzle now” 操作。模式编码在 tensor_map 中，同一条 tiled load 会按描述符选择目标地址生成规律。

DESCRIPTOR-DRIVEN ADDRESSING 
// 指令形式不变；变化在 TensorMap.swizzle
cp.async.bulk.tensor.2d.shared::cluster.global
  .mbarrier::complete_tx::bytes
  [smem_tile], [tensor_map, {x, y}], [mbar];

// 128B 模式的典型 16B chunk 视图：
physical_chunk = logical_chunk XOR (row & 7);

上面的 XOR 仅用于建立 128B 模式的直觉，不应直接推广到所有模式。真实实现必须遵循 TensorMap 的 box、内部维度、SMEM 对齐和 GMMA layout 约束。

3使用场景和原理

对硬件

地址生成器必须同时理解 global box 遍历和 swizzled SMEM 写入，并满足对齐与原子性约束。

对软件

不能再把 SMEM tile 当普通行主序数组；CUTE layout／GMMA descriptor 必须选中同一 swizzle 规律。

Cluster multicast

一次 global 读取 · 多个 CTA SMEM 投递

解决什么

一个 cluster 内多个 CTA 协同计算时，常有两个以上 CTA 需要完全相同的 A 或 B tile。若各自发起 global load，会重复占用 L2／互连带宽，也重复执行地址生成。

1功能定义

Multicast 让一条 tensor load 将同一 global tile 分发到 CTA mask 指定的多个目的 CTA。每个目的 CTA 在自己的 shared memory 中收到一份数据，并用自己的 mbarrier 跟踪事务。

它是 数据复用机制，不是把多个不同 tile 合并成一条 gather，也不是在 CTA 之间广播寄存器值。

2PTX 指令

MULTICAST LOAD · 示意形式 
cp.async.bulk.tensor.2d.shared::cluster.global
  .mbarrier::complete_tx::bytes.multicast::cluster
  [smem_tile], [tensor_map, {x, y}],
  [mbar], cta_mask;

// 各接收 CTA 在本 CTA 的 mbarrier 上登记预期字节数
mbarrier.arrive.expect_tx.shared::cta.b64
  [mbar], transaction_bytes;

cta_mask 决定接收者集合。发起方、接收方、SMEM stage 生命周期与 barrier 相位必须协同；只复制 mask 而没有相应 pipeline 同步，会读到未完成或已被覆盖的 stage。

3使用场景和原理

典型二维 CTA tile 划分中，沿 M 方向的一组 CTA 可共享 B，沿 N 方向的一组 CTA 可共享 A。CUTLASS 因此为 A、B 分别构造 mask，而不是假定两者使用同一广播拓扑。

异步完成机制与多阶段流水

mbarrier · expect_tx／complete_tx · bulk-group · async proxy

解决什么

如果每次拷贝后都全线程同步，异步引擎再快也无法隐藏延迟。TMA 需要一种能按“整块数据是否到齐”同步，并能让 producer／consumer 在不同 stage 上并行工作的机制。

1功能定义

  • Load：生产者在 mbarrier 上登记预期 transaction bytes；TMA 数据到达时执行 complete_tx，消费者等待 barrier phase 完成。
  • Store／reduce：用 bulk_group 将提交的操作分组，通过 wait 等待完成或等待到可读回 SMEM 的程度。
  • Async proxy：普通线程对 SMEM 的写入，需要 fence 才能对后续 TMA 读取可见；TensorMap 的 proxy 可见性另有专门规则。

2PTX 指令

LOAD ACCOUNTING / STORE RETIREMENT 
// 1) 为 load 登记预期到达字节数
mbarrier.arrive.expect_tx.shared::cta.b64 [mbar], tx_bytes;
cp.async.bulk.tensor.2d.shared::cluster.global
  .mbarrier::complete_tx::bytes [smem], [tmap, {x,y}], [mbar];
// 消费者用 mbarrier try_wait / test_wait 等等待 phase

// 2) 普通 proxy 写 SMEM → async proxy 读取
fence.proxy.async.shared::cta;
cp.async.bulk.tensor.2d.global.shared::cta.bulk_group
  [tmap, {x,y}], [smem];
cp.async.bulk.commit_group;
cp.async.bulk.wait_group.read 0;  // 示例：等至可重新读取源 SMEM

wait_group 与 wait_group.read 的等待强度不同：软件复用源 SMEM 前，必须选择满足实际生命周期要求的形式。

3使用场景和原理

为什么按字节记账

一次 stage 可能组合多个 TMA 操作。expect_tx 建立总量，complete_tx 随数据到达抵扣；比逐指令轮询更适合整块 tile。

为什么需要 proxy fence

TMA 与普通 ST 指令属于不同访问路径。程序顺序本身不足以建立 async proxy 对先前 SMEM 写入的可见性。

im2col 与专用数据布局

NWC／NHWC／NDHWC · interleave · W 系列模式

解决什么

把卷积转成 GEMM 时，若显式生成 im2col 矩阵，同一输入像素会因滤波器窗口重叠而被复制多次，产生巨大内存和带宽开销。TMA 可以在搬运激活 tile 时直接形成 implicit-GEMM 所需视图。

1功能定义

im2col mode 面向 NWC、NHWC、NDHWC 等布局，支持 3D～5D 形式，把卷积窗口、padding、halo、dilation 等映射合并进地址生成。输出到 SMEM 的仍是供 GMMA 消费的 tile，而不是一张写回 global memory 的展开矩阵。

Interleave：None／16B／32B

用于通道或分量按 16B／32B 组交错的 global 布局。它描述内存组如何解释，与 SMEM bank swizzle 是正交概念。

W 系列：im2col 地址生成变体

im2col::w、im2col::w::128、im2col_no_offs::w 涉及 wHalo／wOffset 等宽度方向坐标组织；不是另一种卷积算法。

2PTX 指令

// 其他形式族：

im2col 支持 3D～5D，但具体坐标、pixel offset、W 模式操作数与限制必须按所选形式核对。::128 和 no_offs 是更专门的数据组织／坐标变体，不能只改后缀就假定语义等价。

CUTLASS 的三类卷积展示了 tiled 与 im2col 如何组合：fprop／dgrad 中 A 操作数使用 im2col、B 使用 tiled；wgrad 中则 A 使用 tiled、B 使用 im2col。硬件模式服务于数据流角色，而不是绑定某一种卷积方向。

证据边界：本章的实际应用证据聚焦 CUTLASS im2col。interleave 与 W 系列在这里用于澄清硬件语义和设计边界，不声称已在上述生产 mainloop 中验证到对应模式的实际启用。

TMA store-reduce

写回与元素归约合并 · add／min／max／逻辑运算

解决什么

多个 warpgroup 或 kernel 路径产生同一输出的部分结果时，普通流程需要把结果写回，再由另一轮读取、相加、写回。若输出已在 SMEM，直接把“写回 + 与 global 旧值归约”合并，可减少中间流量。

1功能定义

cp.reduce.async.bulk.tensor 从 SMEM 读取一个 tensor tile，并在写向 global tensor 时执行逐元素 reduction。支持 add、min、max、inc、dec、and、or、xor 等操作类别，具体类型与操作组合受 PTX 规则约束。

适用关键是：算法本来就允许按该 reduction 运算合并部分结果，并且 global 输出的旧值是运算语义的一部分。若只是覆盖写，普通 TMA store 更直接。

Tensor prefetch 与 cache hint

L2 预热 · eviction policy · 不占用 SMEM stage

解决什么

有些数据很快会被正式 load，但首次访问延迟会暴露；另一些数据有明显复用规律，默认 L2 淘汰策略未必合适。并非所有提前搬运都应该立刻占用宝贵的 SMEM。

1功能定义

  • Tensor prefetch：根据同一 TensorMap／坐标模型，把对应 global 数据预取到 L2；不写 SMEM，也不向 mbarrier 交付 tensor tile。
  • Cache hint：给 TMA load 附加 L2 cache policy，例如让具有后续复用价值的数据采用 evict-last 策略。
  • Descriptor prefetch：prefetch.tensormap 预热描述符本身，与 tensor 数据 prefetch 是两件事。

2PTX 指令

L2 PREFETCH / CACHE POLICY · 示意形式 
// 只预取 tensor 数据到 L2，不写 SMEM
cp.async.bulk.prefetch.tensor.2d.L2.global
  [tensor_map, {x, y}];

// 正式 load 可带 L2::cache_hint；policy 由合法策略操作数给出
cp.async.bulk.tensor.2d.shared::cluster.global
  .mbarrier::complete_tx::bytes.L2::cache_hint
  [smem], [tensor_map, {x,y}], [mbar], cache_policy;

// 描述符本身的预取是另一条指令
prefetch.tensormap [tensor_map];

3使用场景和原理

Prefetch 是提示，不是流水完成对象

正式计算仍要执行正式 load，并等待该 load 的 mbarrier。不能拿 prefetch 当作“数据已经在 SMEM”的证明。

Cache hint 不是永远越快

EVICT_LAST 适用于有明确复用价值的数据；若把大量流式数据都保留，会挤压其他工作集。

设备端 TensorMap 更新

tensormap.replace · cp_fenceproxy · acquire fence

解决什么

Grouped GEMM 中，同一个 persistent kernel 要连续处理多个 problem；每个 problem 的矩阵地址、形状或步幅可能不同。若每组都回 host 重建 TensorMap，会破坏设备侧调度与流水的连续性。

1功能定义

设备端可以基于一份 TensorMap 模板，使用 tensormap.replace 替换允许修改的字段，例如 global address、global dim、global stride、box 等。更新后的描述符要经过 copy-fenceproxy 与相应 acquire fence，才能被后续 TMA 操作按预期看到。

这不是任意修改 128B 描述符的通用许可：字段、数据类型、对齐、状态和 scope 都必须遵守 PTX 约束。

3使用场景和原理

Grouped GEMM／MoE 类负载的共同特点是 problem 集合在设备侧连续调度。复用描述符模板并原地换组，避免每组都经历 host 往返，也便于保持 persistent pipeline。
